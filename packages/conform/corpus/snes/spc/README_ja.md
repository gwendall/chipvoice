<a id="the-timer-phase-regression"></a>
## タイマーフェーズの回帰テスト

`timer-phase.spc`は`../../../oracles/snes-spc/snes_spc/SNES_SPC.cpp`の
`fix_snapshot_timer_phase()`パッチ（このファイル自身のドキュメントコメント、および
DECISIONS.md #46を参照 - 全体の仕組みを説明しています）に対する回帰テストです。
観測可能な唯一の事象が、CPUがタイマー0のカウンタが非ゼロになったのを初めて見た
正確なサイクルであるようなスナップショットです。タイマー0は周期1（1プリスケーラ
周期、通常テンポで128 SPCサイクル）で有効化されているため、正しいエミュレータは
スナップショット自身のサイクル0から実際に1周期分が経過してからその瞬間に到達し、
それより早くは到達しません。

`check.mjs`はこのファイルの書き込みサイクルを、内容だけでなく正確に検証します。
パッチ適用済みのオラクルの唯一の書き込みはサイクル141に現れ、本パッケージ自身の
SPC700がサイクル140で報告するのに対して1サイクル遅れます（このファイル自身の
先頭コメントに記載されている、同じプリチャージ由来のラベリングの違いです）。
パッチなしでは、blargg自身のsnes_spcはサイクル15で報告します - 約126サイクル早く、
スナップショットが数命令しか実行していないうちにプリスケーラ1周期分が経過した
ものと誤って数えています。これが再発した場合、`check.mjs`自身のこのファイルに
関する報告が、全体の割合が下がるだけでなく、直接それを名指しします。

<a id="the-two-snapshot-restore-regressions"></a>
## 2つのスナップショット復元回帰テスト

`dspaddr-select.spc`と`echo-snapshot-restore.spc`はNEXT-26の回帰テストで、
どちらも`packages/chipvoice/src/spc-import.ts`（2つ目のファイルについては
さらに`chips/snes/sdsp.ts`／`chips/snes/dsp.ts`も）にある、新しいチップが
インポート済みプランの`events`を再生したときにスナップショットの状態を、
そのスナップショットが実際にロードされた場合と異なる形で再構築してしまって
いた2つの経路に対するものです。`importSpc`をローカルの市販SPC吸い出し
（決してコミットしない。DECISIONS.mdを参照）に対してテストすることで
見つかりました。

`dspaddr-select.spc`：DSPADDR（$F2）はS-SMPのラッチ状態であり、スナップ
ショットのレジスタブロックが復元する128個のDSPレジスタの一つではありません。
曲の途中で取得されたスナップショットは、ほぼ必ずCPUの次の命令がDSPDATA
（$F3）にそのまま書き込むところから再開します - 選択する側の書き込みは
スナップショットが取られる前にすでに済んでいるからです。このラッチに値を
与えずにおくと、プランの復元用書き込みを再生する新しいチップは、復元ループ
自身の最後の反復が選択したレジスタ（127）のままになってしまい、このファイル
の唯一の本物の書き込みが誤ったレジスタに着地します。レジスタ復元ループの
直後に、復元イベントをもう一つ（`{addr: 0xf2, value: <スナップショット
自身のDSPADDR>}`）追加することで修正しました。

`echo-snapshot-restore.spc`：S-DSPのいくつかのフィールド - エコーアドレス
ラッチ、ディレクションページラッチ、KONエッジラッチ、エコー履歴とその
リング位置 - は、実チップが通常のレジスタ書き込みではなく1サンプルにつき
一度だけ再導出する隠れた内部状態です。連続再生中はこれらは常にレジスタ
ファイルと同期しています（ずれても最大1サンプル分）。スナップショットの
レジスタファイルは連続して動作していたチップが書き出したものなので、その
瞬間もこれらは同期していましたが、スナップショット形式はそれらを運びません。
プランの通常の$F2/$F3書き込みだけを再生する新しいチップはこの再同期を一度も
トリガーしないため、最初のサンプル - さらにエコーバッファの8深さの履歴を
通じて、リングが一周する8サンプル後まで - は代わりにチップ自身の
コンストラクタの初期値のまま動作してしまいます。このファイルのエコー
バッファには、ESA自身が選択するアドレスのRAMにすでに際立ったサンプルが
1つ置かれています。正しい復元はサンプル0からそれを読み戻しますが、誤った
復元はその位置のリングバッファの古びたゼロが何サンプルも後に自然に上書き
されるまで、代わりにアドレス0から読み込みます（このファイルでは無音）。
`SDsp.restoreInternalState()`（`SDsp.load()`のレジスタ以外の半分で、今回
単独でも呼び出せるようにした）と、予約済みアドレス（$F9）での2つ目の合成
イベントによって修正しました。このアドレスは`SnesChip.write`がプラン
自身の復元用プレフィックスからのみ認識し、実際のS-SMPトラフィックからは
決して認識しません（`dsp.ts`の`DSP_SNAPSHOT_RESTORE_ADDR`のドキュメント
コメントを参照）。

<a id="why-so-small"></a>
## なぜこれだけ小さいか

CPU自体はここよりずっと厳密に検証済みです。256個の全オペコード、ドキュメント記載の全フラグ効果、全サイクル数を、Anomie's SPC700 docに照らして`packages/chipvoice/test/spc700.mjs`で確認しています。このコーパスは実物同士の突き合わせ - 実際のスナップショットを実際の参照CPUに、同じファイルとして通す - であり、主たる証拠ではありません。突き合わせる価値のある再配布可能なSPCが見つかれば増やしますが、それまで何も止まりません。
