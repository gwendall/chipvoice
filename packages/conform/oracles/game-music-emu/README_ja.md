# 参照基準：Game_Music_Emu (`Nes_Vrc6_Apu`)

<p align="center">
  <a href="README.md">English</a> &bull;
  <a href="README_ja.md">日本語</a>
</p>


Shay Green（blargg）のGame_Music_Emu、`Nes_Vrc6_Apu`（Nes_Snd_Emu 0.1.8の一部）で、Konamiの拡張音源VRC6の参照実装です。<https://github.com/libgme/game-music-emu>からLGPL 2.1で同梱しています（[LICENSE](LICENSE)参照）、固定revision `fe8da4b6d3876d7542c2fb69d94487e19836d678`です。リポジトリ内の道具で、ここのものは何も`chipvoice`パッケージへは入りません。パッケージはMITのままです（decision 41）。

<a id="what-is-blarggs-and-what-is-not"></a>
## blarggのコードと本プロジェクトのコード

`gme/Nes_Vrc6_Apu.h`／`.cpp`、`gme/Blip_Buffer.h`、`gme/blargg_common.h`、`boost/`は本人の無変更コードで、素の2A03向けの`oracles/nes-snd-emu`が使うのと同じ分け方です。こちらのものは1ファイルだけです。`main.cpp`はchipvoiceのレジスターログを読み、それで`Nes_Vrc6_Apu`を動かし、各オシレーターの振幅差分を合計して、値のすべての変化を`<cycle> <voice> <value>`として出力します - ボイス0〜2、2つのパルスに続いて鋸歯状波で、`Vrc6Apu.trace`が生成するのと同じ順序です。`main.cpp`内のアドレスからレジスターへのディスパッチ（`reg = (addr - 0x9000) & (addr_step - 1)`、`osc = (addr - 0x9000) / addr_step`、`osc < osc_count && reg < reg_count`のときだけ転送）は、Game_Music_Emu自身の`Nsf_Emu.cpp`（`HANDLE_CHIP_VRC6`）からそのまま持ってきたもので、ここで考案したものではありません。ハーネスは初回使用時にシステムC++コンパイラーで`build/`へビルドします。

<a id="known-limits-of-this-oracle"></a>
## この参照の既知の限界

2005年当時のエミュレーターで、本コアが実装のもとにしているnesdev wikiページより前のものです。`docs/chips/vrc6.md`自身の「数値の意味」は、ボードの数値をこれらと突き合わせて読みます。要点は`gme/Nes_Vrc6_Apu.cpp`から直接読み取ったものです。

- **パルスのデューティ位相は無効化中および「常時オン」モード中に凍結し、再有効化しても決してリセットされません。** `run_square`の位相前進ループは`volume && !gate && period > 4`の間しか動きません；チャンネルを無効化すると同じ関数内で`volume`が0に強制され、モードビットは`gate`を立てるため、どちらの場合もループが完全にスキップされ、位相（`osc.phase`）は単に保持されます。再有効化すると、凍結した場所から再開します。nesdev自身の文章は、実際のVRC6がその逆であることを明言しています：「出力は0に強制され、デューティサイクルは直ちにリセットされ停止する；Eが再びセットされると最初から再開する」 - 本コアはこれを文字通り実装しています（無効化から有効化への切り替わりで`step = 15`）。無効化・再有効化を行う全コーパススクリプトは、これを生の一致ではなく区間ごとのシフトとして測定します。
- **リロードされた周期が4サイクル以下のパルスは一切トグルしません。** 上記と同じ`period > 4`のガードが、ナイキストレート付近の非常に短い周期でもループをスキップします；本コアは、下限なしで文書化された`f = CPU / (16 * (t + 1))`の式に従い、どんな周期でも進み続けます。
- **鋸歯状波のアキュムレーターは無効化時に凍結すらせず、そのまま保持されます；分周器も止まります。** `run_saw`は無効化中（`!(regs[2] & 0x80)`）まったく別の分岐を取り、`osc.amp`（アキュムレーター）にも`osc.phase`／分周器にも一切触れません。nesdevの文章はどちらも実際のVRC6が異なることをはっきり述べています：「Eが再びセットされるまでアキュムレーターはゼロに強制される」（本コアは無効化中、蓄積のたびに一度きりではなく毎回ゼロにします）、そして「ただしEをクリアしても周波数分周器はリセットされない」（本コアの分周器は無効化中も刻み続け、ゼロに保持されるのはアキュムレーターだけです）。鋸歯状波を無効化・再有効化する全コーパススクリプトでは、これが一定位相ではなく、サイクルごとに広がっていく相違として現れます。
- **`$9003`／`$A003`／`$B003`（共有のホールト／周波数スケーリングレジスタと、その未使用の2つのミラー）は黙って落とされます。** `Nes_Vrc6_Apu::reg_count`は3なので、`main.cpp`自身のディスパッチ（`Nsf_Emu.cpp`の実際のプレイヤー統合コードから持ってきたもので、ここでの選択ではありません）は、どのオシレーターブロックのレジスタインデックス3への書き込みも決して転送しません。実際のプレイヤーもこの点にまさに忠実です。この理由からコーパスは`$9003`を一度も書き込みません - 分周器をホールトまたは再スケールしたログは、本コアではなくオラクルの沈黙だけを測ることになります - `$9003`は代わりに`packages/chipvoice/test/vrc6.mjs`自身のユニットテストで、nesdevの文章に直接照らして検証されています。
- **無効化が一切なくても生じる1サイクルのクロッキング順序オフセット。** `script-saw-worked-example`は一度有効化した後Eに一切触れませんが、その1つの区間は全長にわたって一定の1サイクルシフトに収まります - これはどちら側のレジスタ書き込みが、その着地したサイクルで効くとみなされるかという違いであり、挙動上の違いではありません。ここで測定された中で最小かつ最も機械的な相違であり、2A03シート自身のNes_Snd_Emuオラクル README がカスタムNSFレートについて記録しているのと同じ種類のものです。

したがって、これは鋸歯状波の波形、両パルスのデューティ比と周期、そして周波数スケーリングの式については - それぞれ自身のスクリプトの区間ごとのシフトを適用した上で確認できる - 参照実装ですが、無効化されたボイスの位相が正確にどのサイクルにあるかについては、また`$9003`については、まったくそうではありません。

<a id="a-second-oracle"></a>
## 2つ目の参照実装

Mesen 2もVRC6をエミュレートします（自身のソース内`Core/NES/Mappers/Audio/Vrc6*.h` - 実際のMesenはC#ではなくC++です。本チケットの以前の一巡ではここを取り違えており、それが本コード同梱を不釣り合いだと読ませていました）。NEXT-14の2巡目で、素の2A03向けにMesenが既にそうしている（`oracles/mesen`）のと同じように、2つ目の独立した参照実装として追加しました：`oracles/mesen/vendor/NES/Mappers/Audio/`配下に無変更で同梱し、`oracles/mesen/main-vrc6.cpp`で駆動し、`oracles/mesen-vrc6.mjs`でラップしています。これが何であるか、この参照実装には検証できないもの（`$9003`、鋸歯状波の無効化時アキュムレーターゼロ化の挙動、4サイクル以下の周期）、そして測定済みのサイクルオフセット規約については、[`oracles/mesen/README.md`](../mesen/README_ja.md)自身の「VRC6音源（NEXT-14）」の節を参照してください。

<a id="ay-3-8910ym2149-ay_apu-added-for-next-15"></a>
## AY-3-8910/YM2149（`Ay_Apu`）、NEXT-15で追加

同じベンダーツリーには `Ay_Apu`（`gme/Ay_Apu.h`／`.cpp`、同じ Game_Music_Emu チ
ェックアウトの一部、無変更、同じリビジョン
`fe8da4b6d3876d7542c2fb69d94487e19836d678` に固定）も含まれており、これは
`Ay8910`（`packages/chipvoice/src/chips/ay8910.ts`）に対する 2 つのオラクル
の一方で、最初にホストするのは Sunsoft 5B 拡張音源である。`main-ay.cpp` はこ
ちら側のもので、チップ自身の 0-15 のレジスタインデックスで指定された
chipvoice のレジスタログを読み込み（`Ay_Apu::write` は直接それを受け取る -
VRC6 とは異なり CPU アドレスのデコードはここには一切ない）、各オシレーター
の振幅バイトの変化をすべて出力する - `Ay_Apu` 自身の 16 段、約 1.5 dB ステ
ップの `amp_table` で、`write_data_`／`run_until` の内部で値が `Blip_Buffer`
のレコーダーに届く前に適用される。これは、生のテーブル適用前のインデック
スが公開アクセサのないプライベート状態だからである（自身の公開構造体フィ
ールドからその生のインデックスをそのまま読み戻す Ayumi 側のオラクル
（`oracles/ayumi/README_ja.md`）とは異なる）。`chips/ay8910.mjs` の
`ay8910-gme-amp` は、比較前に chipvoice 自身の生インデックスを同一のテーブ
ルに通すチップ側の対応物であり、`AY_AMP_TABLE` は `Ay_Apu.cpp` 自身のコメン
トからそのまま複写している。

`Blip_Buffer.h` のスタブには、このオラクル専用の追加が 1 つ増えた:
`clock_rate()` で、`Ay_Apu::run_until` 自身の「可聴外の高いトーン周波数」最
適化が参照する（このハーネスのために追加された挙動ではなく、実機の挙動であ
る）。VRC6 側のオラクルのスタブには一度も必要なかったものである。固定値
`1789773` を返す - このオラクルを駆動する全ログについて正しい値であり、
Sunsoft 5B はこのリポジトリで唯一の AY/YM ホストであり、NES 自身の CPU クロ
ックに乗っているためである（ヘッダー自身のコメント参照）。

<a id="known-limits-of-this-oracle-specific-to-ay_apu"></a>
### このオラクルの既知の限界（`Ay_Apu` 固有）

`docs/DECISIONS.md` の decision 48 に完全な記録がある。要点は `gme/Ay_Apu.cpp`
自身の「Emulation inaccuracies」コメントから直接読み取ったもので、ここでは
`run_until` をデバッグ計装した複製を用いてサイクル番号込みで確認済みである:

- **固定ボリューム（エンベロープなし）で両ジェネレータとも無効化した
  「DACモード」のログのみが、調整なし・一定オフセットなしで厳密一致とし
  て測定される唯一のカテゴリである。** `Ay8910.outputs` のゲート式は、あ
  るチャンネルのトーンとノイズがミキサーレジスタで両方とも無効化されてい
  る場合に `gate = 1` を無条件に強制するため、その出力はボリュームレジス
  タのみとなり、プリスケールされたティックごとにサンプリングされる -
  `corpus/ay8910/core` はこの根拠でこのオラクルに対して100%一致を示し、
  `ay8910`／`ay8910-gme-amp` がここで `core` として果たす役割はこれだけで
  ある。
- **トーンおよびノイズの周期書き込みは、書き込み時点で分周器の位相を綺麗
  にリセットする代わりに、リセット時のデフォルト（`period_factor`、16）
  から位相の差分を持ち越す。** 本番の書き込みの前に調整用の書き込みを行う
  （サイクル0で全て無効化し、サイクル32以降で実際のセットアップを行う）
  と、結果のオフセットはトーン単独では一定かつ周期に依存しないものになる
  （`corpus/ay8910/edge/tone-sweep.log`：この方法で測定した一定の +15 サ
  イクルのオフセット）。ノイズ単独でも同様だが、両方同時では成り立たな
  い。そして、本プロジェクト自身のレビュー教訓（「オラクルにパッチを当て
  てコア側の挙動を採用させ、それを規約上のマッピングと呼んではならない」）
  こそが、`oracles/game-music-emu-ay.mjs` の `trace()` に、VRC6 に対する
  `oracles/game-music-emu.mjs` 自身の鋸歯状波補正のような、この種の調整依
  存の補正を組み込まない理由である - それはその1つの規約にたまたま従わな
  いスクリプトに対しては、気づかれないまま誤りとなってしまう。`edge/` の
  全ログがこのオラクルに対して `--report` のみである理由はまさにこれである。
- **自身のソースが「エンベロープとノイズの周期の変更は次のリロードまで遅
  延される」と既知の不正確さとして挙げている**点は、本プロジェクト自身の
  調査で実証的に確認済みである: 最初の調整の後にノイズ周期を途中で書き換
  えると、新規のノイズ単独の実行が本来持つ一定オフセットの性質が崩れる。
- **振幅テーブル比較（`ay8910-gme-amp`）にはエンベロープカーブが一切な
  い。** `AY_AMP_TABLE` は16段の固定ボリュームレベルのみをカバーしてお
  り、エンベロープビットが立っているログ（`corpus/ay8910/edge/envelope-shapes.log`
  とその近傍）は `chips/ay8910.mjs` のラッパーには依然として受理される
  が、このオラクルに対する意味のある比較にはならず、`core` のどのスクリ
  プトもそれに依存していない。
- **ノイズを含むログは、タイミングオフセットとは別の理由で `Ay8910` 自身
  のノイズジェネレータと不一致になる。** `Ay_Apu` 自身のノイズ式
  （`(uMinus(lfsr & 1) & 0x12000) ^ (lfsr >> 1)`）はガロア形式の17ビット
  LFSR である。`Ay8910` 自身のノイズジェネレータは代わりにフィボナッチ形
  式を使っている（`chips/ay8910.ts` の `tick()`）。これは MAME 自身のハー
  ドウェア検証済みの構成、および Ayumi の独立した実装と一致する
  （decision 48）。このオラクルのガロア式は、本プロジェクトが見つけた限
  りどこにもハードウェア検証済みとは文書化されておらず、そのためこのジェ
  ネレータについては信頼されていない: ノイズを含むログは他の `edge` ログ
  と同様、タイミングオフセットに加えてこの理由でも、このオラクルに対して
  常に `--report` のみにとどまる。
