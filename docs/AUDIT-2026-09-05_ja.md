<a id="constats-prioritaires"></a>
## 優先的な指摘

<a id="1-p1--un-changement-de-titre-peut-supprimer-larrangement-musical"></a>
### 1. P1 — タイトル変更だけで編曲が失われる

`apps/web/src/studio/useLibrary.ts:185`は`song.patterns[song.order[0]]`だけを読み、全pattern、order、独自chord、intentを編集stateに保持しません。`studio/song.ts:93`は独自和音の単一patternへ再構築し、保存時の`useLibrary.ts:59`も1patternと`order: [0]`を送ります。

本番buildで2pattern、`order: [0,1,1,0]`、`chordShape: [[0,7,12]]`を作り、共有を開きtitleだけ変えてForkすると、1pattern、`order: [0]`、`[[0,3,7],[0,3,7],[0,3,7],[0,4,7],[0,4,7]]`へ変わります。

元の公開曲は保たれますがコピーは音楽を失い、画面再生も既に縮小編曲です。fork APIは省略intentを継承するためDBには残り得ますが、studioでは無視され、試聴とexportの差を拡大します。

**推奨：** 全音楽documentを正本とし、gridは選択patternだけを編集します。title変更では音楽fieldを一切変えません。serverで読んだscoreを渡し、default demoを一度見せる余計なloadも避けます。豊かなscoreのtitle-only forkで全fieldと音を比較します。

<a id="2-p1--stop-et-le-vol-de-canal-ne-neutralisent-pas-les-écritures-déjà-programmées"></a>
### 2. P1 — Stopとボイス借用が予約済みwriteを無効にしない

`packages/chipvoice/src/driver.ts:327`はnote全体を将来writeへ展開し、`stop()`（`:333`）は消音を足すだけです。NES queue（`chips/nes/dsp.ts:751`）は残します。arbiterは新規呼出を防ぎますが送信済みを消せません。

実coreで40 ms停止、45 ms頃音量0、60 msにmusic volume 12が復帰しました。40〜140 msにvolume 3を要求するSFXも50 msで12へ上書きされ、その後も曲envelopeを受けます。既存テストは`canPlay()`と表示だけを見て成功してしまいます。

**推奨：** voiceごとのowner／generationを持つcancel可能な音楽命令と、SFX後の復帰を定義します。register化前に情報を保持します。共有registerがあるためアドレスだけの削除では不十分です。Stop、同時SFX、曲変更後の実write／音を検査します。

<a id="3-p1--la-connexion-mélange-identité-durable-clé-api-et-session"></a>
### 3. P1 — loginが永続identity、API key、sessionを混同

`apps/web/src/lib/auth.ts:48`は同emailでも新key IDを作り、曲と`/api/me`はkeyに属します。再loginで旧公開曲を自動回復できません。「keyがidentity」というコメントは製品上の選択を隠しています。

`redeemMagicLink()`はkey hashを置換します（`auth.ts:102`）。メールにはAPI keyとbrowser link両方があるのに、link前の`/api/me`は200、後は401でした。利用者がlinkを開くとagentのアクセスが失われます。

**推奨：** 安定user、複数API key、独立browser sessionへ分離し、tokenをatomic消費します。現read→update競合はコードで見えますがローカル同時試験では再現していません。所有者を変えず回復、一覧、失効を可能にします。

<a id="4-p2--léditeur-texte-réécrit-la-saisie-à-chaque-caractère"></a>
### 4. P2 — text editorが毎文字入力を再構築

`apps/web/src/studio/App.tsx:337`は正規化scoreを表示し、各`onChange`で分割、空白除去、64セル補完をします。空にして`C5 D5`を順次打つと、期待した2音でなく多数の点と末尾`.C5D5`になります。`fill()`で全行を入れる検査では見つかりません。

**推奨：** 空白と一時的な不正文を保つ独立text draft、診断付きvalidation、明示または適切な時点のapplyを用意します。各打鍵を即座に有効scoreへ強制しません。

<a id="5-p2--les-gestes-et-le-clavier-ne-correspondent-pas-au-contrat-de-la-grille"></a>
### 5. P2 — gestureとkeyboardがgridの契約に合わない

`Grid.tsx`は`onPointerDown`だけで`onClick`がなく、focus cellのEnterはChromiumで無反応、Spaceは全体transportに奪われます。携帯cell幅は12pxでnoteを隠します。20セル以上を求めるmobile testは操作精度を下げる密度を褒めています。

touch開始で即paintするため、tapとscroll／pinchの開始を区別できません。

**推奨：** semantic keyboard起動、focus管理、tap確定後編集。密なoverviewと大きな編集面を分け、16セルという数だけを携帯基準にしません。Undo／Redoとlocal自動draftも必要です。

<a id="6-p2--le-cache-audio-ne-respecte-pas-le-contrat-annoncé"></a>
### 6. P2 — 音声cacheが説明した契約を満たさない

現engineで生成した音を`public, max-age=31536000, immutable`で返します（`apps/web/src/app/api/audio/[id]/[format]/route.ts:83`）。決定10は同URLのbytesがdeployで変わると認めています。score不変でもengine／arranger変更でrenderは変わり、CDN purgeはbrowser cacheを消しません。

DB削除はoriginでの新renderを防ぐだけで、fresh cacheの応答を取り消せません。削除で音声配信が止まるという説明は限定が必要です。

**推奨：** `/s/{id}`は安定linkにし、engine／arranger／profile／format／option別の音声資源を区別します。公開時の音を固定するか新engineを適用するか明示します。旧URLのresolverで互換を保てるのでversion化はlink破壊を意味しません。[Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)参照。

<a id="7-p2--la-conformité-peut-réussir-sans-la-baseline-demandée"></a>
### 7. P2 — 要求baselineなしでも適合性が成功

`packages/conform/src/cli.mjs:141`はfile不在で比較を省略しますが、`:171`のexit判定はoptionの存在だけを見ます。再現コマンド：

```sh
node packages/conform/src/cli.mjs 2a03 \
  --corpus packages/conform/corpus/2a03 --only script-linear \
  --baseline /tmp/chipvoice-audit-nonexistent-baseline.json
```

一致0.8936%の相違を示してexit 0になります。この%だけでchipが悪いとは言えず、ここで示すのはbaseline未確認です。欠落／追加caseやvoiceも固定されていません。

**推奨：** 指定baselineの不在／不正は失敗させ、case、voice、duration manifestとoracle／corpus版を確認します。厳密一致、時間整合、説明済み差を区別します。

<a id="autres-points-techniques"></a>
## その他の技術的指摘

- **低レートrender：** `render.ts:95`の4096sampleは8 kHzで512 ms、先読みは200 ms。計測coreで必要blockの後にnoteが届きました。block終端まで予約するかrateに応じblockを変えます。
- **Timeline：** `Sequencer.pump()`の位置履歴purgeが`positionAt()`依存で、表示readerなしでは蓄積します。UIと独立にpurgeします。
- **Validation：** `validate.ts:246`は`voice`を使わず、実音域を確認しません。PSGはperiodを黙って制限します。構文検証の後、機種別diagnostic付きarrangeを提案します。
- **Package API：** `Score.chip`で`arrange()`しても得た`Song`にtargetがなく、`renderSong()`へ再指定しないとNES既定へ戻ります。編曲結果にtargetを保持します。
- **Frontend音声競合：** `useChip.start()`がpending creationを共有せず多重生成／古いchip完了が起こり得ます。共有promiseとcancel generationを加えます。`setTrack`更新関数内のpreview副作用も純粋性に反します（[React契約](https://react.dev/reference/react/useState)）。
- **Export：** MP3 mono、API stereoなし、ID3は常にRicoh 2A03。試聴と選択機種へ揃えます。
- **Server計算：** render／encode同期、音声GETにlimiterなし、1〜300秒連続値でcache variant増大。単発local測定の2秒音声にNES約2.83 s、DMG 2.93 s、MD 6.94 s、SNES 1.97 s、C64 1.83 sかかり、「1分音声＝CPU 1秒」を支持しません。server benchmarkではありません。profile、variant上限、同時dedupを行い、測定に応じworker／保存を追加します。
- **DB：** 初回の臨時migration、区別せず握るALTER error、実3表なのに1表というコメント。小さなversioned migrationで十分、SQLite／Turso置換は不要。
- **CI：** DSPは厚いがWeb3suiteと本番Webbuildが`ci.yml`にありません。一時DBの短いbrowser経路で内部stateでなく観測結果を検査します。

## 維持する設計と改善する境界

monorepo、独立package、digital／analog分離、cycle event、機種driver／arranger、読めるscore、不変fork、native oracleの独立harnessは維持します。全面rewrite、新framework、microserviceでは指摘を解決できません。

明確にする境界は次の4つです。

1. API、editor、共有、render共通のversioned音楽正本文書。
2. 原intentを失わず明示targetとdiagnosticを出すarranger。
3. 共通時計とStop／SFX／chip変更の定義を持ち、eventを所有／cancelするtransport。
4. 編集state、入力途中text、再生stateを分けるUI。

「2チップ」「NESだからmono」「1表」「studioとMP3が同じ」など古い説明を整理します。局所制約はコメントに、歴史は置換済みと明記した決定へ移します。

<a id="readme-et-crédibilité-des-preuves"></a>
## READMEと証拠の信頼性

root READMEは目的とanalog制限をよく説明しますが実例が遅く、npm READMEは2チップ／第2予定、descriptionはNES中心、SCOREは第3予定のままです。MITの断言も合成ライセンスと2LGPL portに一致しません。配布fileへ説明を合わせる必要があります。本監査は法律分析ではありません。

短い約束、demo、実行／export例、5機種と能力、忠実度制限、詳細docsの順を提案します。能力一覧を共通sourceから生成し、「他に存在しない」より実証した機能を示します。

portと元実装の一致はコーパス内の移植品質の強い証拠ですが、全実機挙動の独立測定ではありません。異なる尺度の平均Done%は誤った精密さを与えます。coverage、oracle／version、厳密一致、整合、実機測定を別表示します。

<a id="backlog-proposé"></a>
## 提案するバックログ

新機種を止める決定19は適切ですが、phase 8の14ticketは修復、初回体験、editor、live、MIDI、exportを混在させています。metricsは最後でなく次を選ぶため早期に入れます。

**単位1 — 信頼性。** score、Stop／SFX、text、identity、baseline不在失敗と回帰。豊かな曲がlink→fork→renderで保持されStopが無音になること。

**単位2 — 最初の1分。** 明示試聴、機種差を示す曲、見える5選択、role intent、携帯編集、Undo／Redo、draft。説明なしに聴く／比較／変更／共有でき、この段階から測定すること。

**単位3 — 音楽の豊かさ。** P4-7とSNES triad、FM drum、SID filterを結び付けます。正しいsynthだけで機種を特徴付けるarrangeになるとは限らず、人の試聴で数値を補います。

**単位4 — 配布。** versioned render契約、stereo／tag、server計算制御、npm docs。利用に応じcache修正を単位1へ早めます。

MIDI、stems、新systemは利用検証後です。不要なのではなく、既存経路の信頼性より価値の根拠が少ないためです。

<a id="idées-à-challenger"></a>
## 挑戦すべきアイデア

- **どこでも初clickで音：** 大きい試聴か明示note／padを使います。titleやlogin clickは音楽開始の同意ではありません。
- **固定scale：** 補助modeと半音階を両立し、借用音と経験者の作曲を妨げません。
- **4役割＝4ボイス：** 単純な4role UIを保ちつつ、機種が許せば和音に複数voiceを使い、C64共有妥協を表示します。
- **5機種比較：** 同じ位置と近い試聴levelで同フレーズを比較する方が長い忠実度説明より直接的です。機種専用曲で補います。
- **編集相手としてのagent：** 短い例、局所変更、実用的diagnosticを提供します。「サビを緊張させる」で文書全体を再生成せず構造を保てるべきです。
- **real-timeとoffline同一：** 同じDSPでも入力eventが違えば音は違います。操作中の出力結果で検査します。

次の成功は具体的です。曲を開き、正しい曲を聴き、機種を変え、1音を編集し、必要なら戻し、直前に聴いたものをそのまま共有できることです。
