# 操作から再生までの遅延監査

[English](INTERACTION-LATENCY.md)

2026-09-08。本番の `2cdf7b3`（PR #55）を調査した。これは調査と音声準備の試作であり、リアルタイムプレーヤーへの移行を完了したという報告ではない。

## 測定結果

開発用 Mac の Chromium / Playwright で `https://chipvoice.dev` を確認した。トップ、ループ編集、作曲、ラボはそれぞれ新しいブラウザーセッションを使用した。アカウント作成、生成、公開、本番データの変更は行っていない。開始時のロードアベレージは 5.35 / 6.71 / 11.83。少数回の診断測定であり、機種別ベンチマークや p95 値ではない。

| 操作 | 観測した遅延 |
| --- | --- |
| トップで Mario を初めて再生 | 2.04〜2.60 秒 |
| 初めて Game Boy を選択 | 1.02〜1.89 秒 |
| キャッシュ済みの機種・曲を選択 | 181〜182 ms |
| Mario / Game Boy のテンポを 100% から 125% に変更 | 7.15〜12.38 秒 |
| Zelda / Sonic の初回選択 | 1.87 / 2.72 秒 |
| 作曲画面の初回再生 / テンポ変更 | 1.14 / 0.89 秒 |
| 作曲画面で初めて Game Boy を選択 | 2.51 秒 |
| ループ編集のテンポ / 機種変更 | 272 / 277 ms |
| ラボの初回再生 / Game Boy | 0.78 / 1.14 秒 |
| ラボのキャッシュ済み Super Famicom | 1 ms |

ループ編集以外は、入力から `AudioBufferSource.start()` の呼び出しまでを測定した。実際の開始はさらに 25 ms 先に予約される。ループ編集では新しいエンジンが current になるまでを測定しており、クロスフェード完了とブラウザーのポーリングも含む。これらはスピーカーで測定した遅延ではない。動作中のブラウザーは約 168 ms の出力遅延を報告した。

負荷や通信によって計算時間は変わるが、180 ms の待ち時間は再現した。トップは全体を 2 回、キャッシュ済み選択を中心に追加で 1 回測定した。タイトルだけを変更しても音声は再生成されなかったが、作曲画面の固定プレーヤーには古いタイトルが残った。

トレースとデスクトップ画像は `.artifacts/interaction-latency/` に保存した。最初の結果は直下の `measurements.json`、後続の結果はモード別ディレクトリにある。作曲画面の再測定には移調とパート音量の変更も含む。

## 原因

1. **対話操作が書き出し完了を待っている。** トップと `ProjectPlayer.load()` は曲全体の PCM を生成し、WAV に変換し、Blob を作り、AudioBuffer にデコードしてから切り替える。テンポ変更では 70.83 秒分の音声を先に計算した。この操作中、メインスレッドの long task は記録されなかった。移調、ソロ、ノート編集、パート調整も同じ経路を通る。
2. **キャッシュにも固定待機がある。** トップは準備済みの曲・機種にも 180 ms の debounce を適用する。作曲画面も 180 ms、ループ編集は 45 ms 待つ。ループの切り替えはその後 100 ms 先に開始し、185 ms で引き継ぎが完了する。クリック防止用の短いフェードと、操作開始を遅らせる待機は別の問題である。
3. **再生しない音声も待つ。** Mario の初回再生では自作レンダリング 3.37 MB と独立参照音源 3.47 MB の両方を取得・デコードした。参照音源の障害が通常再生を妨げる可能性がある。Game Boy の楽譜表示データは二重取得され、音声取得も表示データを待っていた。
4. **編集設定に対応したキャッシュがない。** 8 個の URL をキャッシュしても、編集ごとに Worker と Blob URL が新しくなるため、同じ設定に戻しても再計算する。90 秒・44.1 kHz・ステレオ Float32 を 8 個保持すると、PCM だけで約 254 MB になる。個数制限だけではメモリー上限にならない。
5. **ループ編集もエンジンを作り直す。** 音楽内容の変更時には新しい `Chip` を生成してクロスフェードする。Worklet モジュール自体は AudioContext ごとに既にキャッシュされている。テンポやミュートには、未来のイベントの取消しと適切なリリースを含む差分更新が必要になる。
6. **公開曲にも直列処理がある。** 公開ページが持っている曲情報を再取得してから音声を読み込む。音声 API は DB の全チャンクを結合してから応答し、Range に対応せず `private, no-store` を返す。HTML のメディア要素は受信途中から再生できるが、サーバー側では既に全ファイルを読み終えている。調査時の公開一覧は空だったため、この項目はコード確認であり、本番の公開曲を測定した結果ではない。
7. **状態通知とメタデータにも改善点がある。** 固定プレーヤーは 50 ms ごとに準備状態を確認する。作曲画面のタイトルはレンダリング済みスナップショットに結び付いている。同じ曲の名前変更は音声と独立して反映し、別の曲へ切り替える間は実際に鳴っている曲を表示する必要がある。

連続再生、取消し規則、出力時刻に同期する表示、独立参照音源の忠実性は維持する。フェードをなくしたり、視覚表示だけ先に進めたりしても解決にはならない。

## 段階的レンダリングの試作

ブラウザー内の Worker で Mario の 125% テンポの全コマンドを計画し、既存の `ChipCore` で最初の 4,096 フレーム（92.9 ms 分）だけを生成した。128 フレームずつ生成した結果を、既存のオフライン処理が 4,096 フレーム単位で生成した結果と比較した。

| 機種 | 計画・初期化・先頭ブロック生成 | PCM 最大差 |
| --- | --- | --- |
| Famicom | 37.5 ms | 0 |
| Game Boy | 30.7 ms | 0 |
| Mega Drive | 58.5 ms | 0 |
| Super Famicom | 30.2 ms | 0 |

先行する単一ブロック版では 40〜86 ms だった。Worker 起動、取得、音声出力、初回の再生許可は含まない。最初の音を作るために曲全体の PCM を待つ必要がないことは確認できた。ただし、長時間の安定動作、途中からの移動、滑らかなパラメーター変更、曲全体の忠実性まで検証したわけではない。

`ChipCore.schedule/load/render` を使い、同じコンパイラーと DSP をオフライン書き出しと共有する。候補は、上限付き PCM キューを使う Worker と、直接処理する AudioWorklet。前者はバッファ不足への対策、後者は各音声処理期限の厳守が必要になる。別の楽譜解釈器を作ったり、多声部の曲を 4 ロールに縮約したりしない。

## 実装順序

| チケット | 内容 | 合格条件 |
| --- | --- | --- |
| LAT-1 | 準備済み選択の待機を除去。同じ選択は無処理。表示取得を統合し音声と並行化。タイトル更新を独立させる | 制御した環境で準備済み選択が 100 ms 未満。名前変更で DSP 処理が発生せず表示が更新される。表示データの二重取得なし |
| LAT-2 | 参照音源を比較時に取得。ソース改訂・エンジン版・サンプルレート・音楽設定をキーにキャッシュ。次の候補だけを先読み | 参照音源の遅延・障害で通常再生が止まらない。同じ編集設定への復帰で再生成しない。バイト数と時間の上限を守る |
| LAT-3 | コンパイルと WAV 書き出しを分離。同じコアで段階的プレビューを実装 | 全曲 PCM・WAV・デコードを待たずに最初の音を出す。全機種でオフライン PCM と比較。長い MIDI でもメモリーと処理時間を管理 |
| LAT-4 | テンポ、音色、ノート、音量、ミュートを差分更新。互換エンジンを再利用し準備状態をイベント通知 | 全曲再生成なし。音切れ・クリック・古いイベント・鳴りっぱなしなし。素早い操作でも Pause が優先。ブロックごとの割り当て増加なし |
| LAT-5 | 曲途中の機種変更とシークに対応する状態保存。機種ごとの能力と上限付きキャッシュ | エンベロープ、ノイズ、サンプル位置、フィルター、エコーを維持。通常再生と状態復帰を比較し、ネイティブコマンドと拍位置も検証 |
| LAT-6 | 公開曲の情報を再利用。バイト範囲要求と部分読み出し。改訂済み音声のオブジェクトストレージを検討 | 全 DB 音声の読み出しを待たずに再生・シーク。範囲応答と早期転送をテスト。非公開・取消しの権限を維持。一覧全体を先読みしない |
| LAT-7 | 遅延と音声の E2E 回帰評価 | 全表示機種、初回・再訪、連続操作、モバイル、出力時刻、取消し、画面遷移、ループ境界、CPU、メモリー、バッファ不足、長曲を確認 |

LAT-1/2 はすぐに改善できる。根本原因は LAT-3/4 で解消する。曲途中の瞬時切り替えを約束する前に LAT-5 が必要になる。レジスター値だけでは DSP の完全な状態にならず、共通コアには現在 save/restore 契約がない。途中のノートから新品のチップを鳴らしても、それ以前の履歴が失われる。LAT-6 は独立して進められる。LAT-7 は今の診断から段階的に拡張する。

目標は UI の即時応答と、準備済み操作に対するアプリ追加遅延 50〜100 ms 未満。これは提案値であり現状の保証ではない。未取得の音源、初回再生許可、機器や Bluetooth の遅延を含む万能な「ゼロ秒」は保証できない。準備中は前の音声を継続する。BPM のために `AudioBufferSource.playbackRate` を変えると音程も変わる。独立ステム化も、非線形ミキサーや共有エフェクトへの影響を検証してから行う。

## 再実行

`apps/web` で実行する。診断は本番への読み取りとブラウザー内の一時編集だけを行い、公開やメール送信はしない。

```sh
PLAYWRIGHT_BROWSERS_PATH=../../.artifacts/playwright MODE=landing node scripts/diagnose-interaction-latency.mjs
PLAYWRIGHT_BROWSERS_PATH=../../.artifacts/playwright MODE=live node scripts/diagnose-interaction-latency.mjs
PLAYWRIGHT_BROWSERS_PATH=../../.artifacts/playwright MODE=create node scripts/diagnose-interaction-latency.mjs
PLAYWRIGHT_BROWSERS_PATH=../../.artifacts/playwright MODE=lab node scripts/diagnose-interaction-latency.mjs
PLAYWRIGHT_BROWSERS_PATH=../../.artifacts/playwright node scripts/diagnose-progressive-preview.mjs
```

`SITE` で対象を変更できる。`WARM_ONLY=1` は時間のかかる編集曲の測定を省略する。`ENFORCE_WARM=1` はキャッシュ済み選択が 100 ms 以上なら失敗させる。監査対象の版では失敗する想定である。試作は先頭区間の PCM 完全一致を検証する。性能診断は並列実行しない。本監査ではフロントエンドや実行時コードの変更・デプロイは行っていない。

## 実装と検証

上の測定は変更前の値です。トップ画面では準備済み選択の 180 ms 待機を廃止し、楽譜と音声を並列に取得します。楽譜リクエストを共有し、比較用の原音は明示的な比較時だけ取得します。デコード済み音声は最大 8 件かつ 96 MiB、コンパイル済みプランは最大 8 件かつ 24 MiB に制限します。

編集後の曲と作曲画面は同じコンパイラ・音源コアによる逐次 PCM 再生を使います。WAV はダウンロード時だけ生成します。最大 3 ワーカーを再利用し、各 PCM キャッシュは約 3 秒に制限します。古い計算は最新入力に置き換え、100 ms を超えて妨げる古い処理は終了します。応答のリビジョンを検証し、前の曲の PCM が再利用後のキャッシュに混入することを防ぎます。

任意の `ChipCore.fork()` が完全な DSP 状態を複製します。内蔵 5 音源は対応し、未対応の追加音源は初期状態から再生して位置を復元できます。保存形式ではなくプロセス内の状態です。エンベロープ、サンプル位置、ノイズ、フィルタ、エコーを維持し、各バリエーションは最大 25 個の粗いチェックポイントと直近 4 個を保持します。

ループ編集は入力を 1 フレームにまとめ、25 ms 先に短いフェードで切り替え、最大 2 つの worklet を再利用します。任意のレジスタ列をその場でリタイミングする API ではありません。変更後の音楽は再スケジュールし、既存の音響的意味を維持します。

公開曲は取得済みメタデータを再利用します。音声の GET/HEAD はバイト範囲と必要な DB チャンクだけの読み出しに対応し、キャンセルすると取得を停止します。非公開・取り消し済みデータの認可は引き続き毎回確認します。

検証には 5 音源および Mario・Zelda・Sonic のネイティブデータの PCM 完全一致、遅延ワーカーの競合、一時停止・再生中の切り替え、比較原音のキャンセル、非公開ジョブのバイト範囲、ブラウザの編集・シーク・終端・再生再開・破棄を含めます。未準備の曲中設定は DSP 履歴の再構築が必要です。その間は現在の音を維持します。通信、機器、OS による停止まで含めた「常に遅延ゼロ」は保証しません。
