# Commodore 64：MOS 6581 SID (`c64`)

<p align="center">
  <a href="c64.md">English</a> &bull;
  <a href="c64_ja.md">日本語</a>
</p>


6581は3ボイスを備え、各ボイスに組み合わせ可能な4波形の発振器とゲート付きエンベロープがあります。隣接ボイス間の同期とリング変調、共有フィルターを使えます。方法は[CONFORMANCE.md](../CONFORMANCE_ja.md)にあります。

| **状態** | **作業中**：各ボイスのデジタル2値がreSID-fpと一致、ドライバーは全役割を再生、アナログ段は資料由来のプロファイル |
| **コア** | 資料から独自実装（`packages/chipvoice/src/chips/c64/sid.ts`）。アナログプロファイルは`dsp.ts` |
| **コアのライセンス** | MIT。参照のreSID-fpはGPLで、ハーネス内だけに置く（決定18） |

**数値の意味。** 全6ストリームの全ログが一致します。全波形の各音高とパルス幅、4組み合わせ波形とノイズ合成時のレジスタへの書き戻し、8レートのノイズとtestビットによるリセット、全ADSRレートとサステイン、各段で数サイクル間隔のゲート、アタック中に現在値より低く設定するレートレジスタ、同期済みの源を含む4比率での同期／リング変調、源のtestビットとゼロ周波数、ドライバー経由2曲を検査します。

初回に直した点は実機の事実に関する2点です。電源投入はリセット線の解除でノイズを1回進めます。またエンベロープのレート8はデータシートの391でなく392サイクルで、kevtrisが実チップから読んだ値に一致します。組み合わせ波形は各組み合わせ6数値のモデルで、全4096項目が参照表と一致します。`pnpm --filter chipvoice-conform fit:c64`で採点します。

この表で新しい4スクリプト（`script-dense-sawtooth`、`script-dense-triangle`、`script-dense-noise`、`script-dense-combined`）は、鋸歯状波・三角波・ノイズ・組み合わせ波形のいずれかをログ全体を通して3ボイス同時に保持します。ほかのスクリプトが検査対象のボイス以外でパルスを使うのに対し、これらは数秒間、全ボイスの12ビット出力がほぼ毎サイクル同時に変化し続けます。これらもreSID-fpと一致します。追加した理由は、以前のハーネスがストリームの全変化を1個ずつオブジェクトとしてメモリに保持していたためです。3つの鋸歯状波を8秒（このコーパスの3倍の長さ）保持しただけでメモリ不足になっていました。typed arrayの列を使う`ChangeStream`とストリーミング比較への変更でこれを解消しました（P7-11）。その厳密なケース、3つの鋸歯状波を8秒間は、このコーパスには含めていません。単独で約1分と1.5ギガバイトほどかかり、上記全部を合わせた数秒間とは釣り合わないため、代わりにオンデマンドで`pnpm --filter chipvoice-conform check:c64:dense`（`packages/conform/corpus/c64-dense`）として実行します。これも一致しており、`check:c64`にもCIにも含まれません。

フィルター用（P7-9）に1スクリプトと1曲を追加しました。`script-filter`は`$D415`-`$D418`に直接書き込みます。2ボイスがフィルターを共有しレゾナンスとカットオフが動く一方、3番目のボイスは3モードを順に切り替えます。`song-filter`はフィルターに到達する2つのアレンジャー語、`lead: "sweep"`と`bass: "resonant"`を再生します。いずれもデジタルトレースを動かしません。フィルターはDACの後段、下記のアナログ段のみに属し、コーパスでは測定できないためです。しかし上記6ストリームではいずれも一致します。ボイスをフィルターに通すかどうかは`osc`／`env`への書き込みを変えないからです。これらが存在するのは、コーパスがドライバーの到達する全レジスタへの書き込みを持つようにするためであり、フィルターが実際にどう聞こえるかは、下記「アナログ段」にある未測定の6581プロファイルのままで、この表が語れることではありません。

<a id="the-8580"></a>
## 8580

C64の後半世代（65とC64C）に載った第二のSID：レジスタとエンベロープジェネレーターは同じですが、組み合わせ波形ビットの引き合い方が異なるデジタル波形ジェネレーター、フローティング波形出力とノイズレジスタのtestビットリセットの両方でコンデンサー放電が長く、6581の折れ曲がったDACに対しほぼ線形なDAC、そして自前のフィルターを持つ、新しいプロセスで作られた再設計チップです。以下の各事実は資料または参照表への実測によるもので、reSID-fp自身の8580ソースを本パッケージへ移植したものではありません（decision 41）。各項が出典を示します。

**選択方法。** `Chip.create`、`renderPerformance`、`renderProject`、または楽曲の`settings.model`で`model: "8580"`を指定します。既定の`"6581"`が使えるところならどこでも：

```js
const chip = await Chip.create(ctx, { chip: "c64", model: "8580" });
```

`ChipCreateOptions`を通じてワークレットの`SidProcessor`の`processorOptions.model`、ハーネスや`RenderOptions`／`renderPerformance`自身の`model`フィールドの`c64Chip.digital({ model })`まで伝わります。未知の値は6581にフォールバックします。`SID_8580_PROFILE`と`SID_6581_PROFILE`（`packages/chipvoice/src/chips/c64/dsp.ts`）も、`Chip.create`を経由せずプロファイルを読みたい場合に直接エクスポートされています。

**組み合わせ波形。** 6581と同じ6数値の隣接引き合いモデル、`COMBINED_8580`（`packages/chipvoice/src/chips/c64/sid.ts`）を、reSID-fp自身の8580表に対して独立に適合（`pnpm --filter chipvoice-conform fit:c64 -- --model 8580`）させたもので、reSID-fp自身の`WaveformCalculator.cpp`の8580用`config[1]`の値をそのまま写したものではありません（decision 41：そのファイルは何を測るべきか知るために読んでよいが、移植はしない）。6581自身の数値から1回だけ降下させると4つのうち3つで収束不足だったため、多数のランダムな開始点からの座標降下で各組み合わせの最良値を採用しています。

| 組み合わせ | reSID-fpの8580表との一致率 |
| --- | --- |
| `saw+triangle` | 99.05 % (4057/4096) |
| `pulse+triangle` | 97.51 % (3994/4096) |
| `pulse+saw` | 95.00 % (3891/4096) |
| `pulse+saw+triangle` | 92.60 % (3793/4096) |

いずれも6581の100%には届きません。reSID-fp自身の8580コードは、両チップに使うこの単純なバイアス／ビットごとの引き合いモデルより詳細なトランジスタモデルから表を作るため、完全な適合は期待できません。上のデジタル一致率のブロックはこの不足がどこに現れるかを正確に示しています。組み合わせ波形を選ぶ2ログ、`script-combined`と`script-dense-combined`だけが98.98%と91.19%になり、それ以外は全て100%一致のままです。上の「実機6581との組み合わせ波形比較」に相当する8580版はありません。`libsidplayfp/combined-waveforms`は8580個体もサンプリングしていますが、それを取得して採点することは本チケットの範囲外で、アナログ段を測る誰かに向けて開いたままです（P7-8）。

**波形タイミング。** reSID-fpの`WaveformGenerator.cpp`／`.h`（既存モデルが使う6581R3の定数の隣にある`FLOATING_OUTPUT_TTL_8580R5`／`SHIFT_REGISTER_RESET_8580R5`）から引いた2つのコンデンサー放電時間：波形未選択のフローティング出力がゼロに落ち着くまで8580は6581の約10倍、testビットによるノイズレジスタのリセットは約13倍かかります。いずれも`sid.ts`の`FLOATING_TTL`／`NOISE_RESET`というモデル別定数で、新しい数式ではありません。同じく`WaveformGenerator.h`より：8580には鋸歯状波の組み合わせでのアキュムレーターのプルダウン（6581限定の効果）も、testビット解除時のノイズ書き戻しにおけるswap-exclusion（同じく6581限定）もなく、いずれも`Oscillator.compute()`／`writeControl()`内で`model`により分岐します。

**OSC3の1サイクル遅延。** `WaveformGenerator.h`の`tri_saw_pipeline`：8580では`$D41B`（OSC3）が返す値は、波形ジェネレーター自身のその周期の出力より1サイクル前の鋸歯状波／三角波パイプラインの値です。6581にはこのパイプラインがなく、現在の周期の値を返します。これはレジスタの読み戻しだけの話で（`Sid`クラスが`output`と別に持つ`osc3`フィールド）、音声出力自体は変わりません。

**DAC。** `SID_8580_PROFILE.ladderRatio = 2.0`、`ladderTerminated: true`は、reSID-fpの`Dac`ドキュメント（「非常に精密に一致」、不連続点なし、比は約2.0）からのものです。この比で終端されたラダーは正確に2の累乗の重みになるため、8580の12ビットDACは（この資料の精度の範囲で）線形で、6581の未終端2.2ミスマッチとは異なります。

**フィルター。** `SID_8580_PROFILE.cutoff`、`qLow`、`qHigh`は、素のreSIDの`filter.cc`（同じファイル、NEXT-04が示した同じ「CSG 8580R5 1690 25」の個体）から導きます。6581の折れ曲がった曲線と異なり、`filter.cc`自身の固定小数点式`w0 = 82355 * (fc + 1) >> 11`（`Hz = 12500 * (fc + 1) / 2048`）は正確な直線で、レジスタの両端はfc=0で6.1035 Hz、fc=2047で12500 Hzです。`qLow`／`qHigh`（0.7072／2.5924）も同じファイルの`_1024_div_Q_table`の最初と最後の固定小数点値から得て、同じ式で計算した閉形式`1/Q`と照合済みです。これは`filter.cc`自身の公開済みの表を測定データとして使うもので（decision 41：読むが移植しない）、NEXT-04が求めた通りです。実機8580のライン出力キャプチャではなく、測定した両端の間の形（6581の曲線は1024付近に折れ曲がりがあります）はまだ未確認で、6581と同じP7-8のキャプチャが必要です。

**未測定のまま残るもの。** 6581と同様、自前の実機8580のライン出力キャプチャはありません。上の「実機6581との組み合わせ波形比較」のような、名前付き実機8580に対する組み合わせ波形の独立検証もありません。測定した両端の間のフィルターの形が本当に`filter.cc`の固定小数点式通りの直線か、6581のように折れ曲がりがあるか。そしてADSR表、ノイズLFSRのタップ、ゲート／同期／リング変調ロジック：reSID-fpの`EnvelopeGenerator.cpp`に8580固有の分岐はないため、本パッケージも6581節のエンベロープと同期／リング変調の事実をそのまま引き継いでおり、8580固有の資料での独立確認はしていません。

## PSID/RSIDの再生

`importPsid`／`renderPsid`（`packages/chipvoice/src/psid-import.ts`）は、PSIDまたはRSIDファイル（HVSCの`SID_file_format.txt`）のINITとPLAYの機械語コードを、資料から書き起こした6510（`packages/chipvoice/src/chips/c64/cpu6510.ts`）と最小限で開示済みのC64環境上で実際に実行し、曲がSIDへ行ったすべての書き込みを`importVgm`と同じ形の`PerformancePlan`として返します。`renderPerformance(plan, c64Chip, {model: plan.model, clockHz: plan.clockHz})`でレンダリングでき、`renderPsid`なら一度の呼び出しで済みます。`psid-import.ts`は`vgm-import.ts`と同じくトップレベルのまま、CPUは他のどのチップのコアとも同じく`chips/c64/`配下に置きます。どちらも`scores/mixing/calibrate.mjs`自身の呼び出し経路には無く(キャリブレーションはチップの音符レベルの`ChipCore`だけを駆動し、このインポート／CPU経路には触れません)、そのためエンジンハッシュに重みを追加しません。

適合性確認は、出荷または移植されたGPLコードを一切含まない3本柱に基づきます（decision 41）：公開されたオペコード／サイクル表と6502.orgの10進モード資料に基づく手書きの単体テスト。Klaus DormannとBruce Clark自身の自己検証型6502テストプログラムを、`packages/conform`内の非公開の適合性確認ツールとしてベンダリングし、この同じ`Cpu6510`に対して実行するもの。そして本チケットから加わった独立参照実装（オラクル） - libsidplayfp自身をピン留めしたリビジョンでクローン・ビルドし、gitignore対象の`.artifacts/`ディレクトリに置く（`scores/psid-corpus/native-oracle.mjs`。Game_Music_Emuに対して`scores/arrangements/native-oracle.py`が使うのと同じピン留めクローンのパターン）。`packages/chipvoice`には一切同梱せず、ベンダリングもしません。

オラクル自身のSID書き込みトレースは、ログをパッチで仕込むのではなくlibsidplayfpの公開`SidConfig::sidEmulation`フックを通して差し込んだもので、INITの呼び出し規約を推測のままにせず実測で確定させました：`A`（曲番号、0始まり）と`P`（`PHP`前の0x24）は、libsidplayfp自身の参照ドライバーと厳密に一致します。`X`と`Y`は一致せず、いまや本当に未定義であることが確認されています - ファイル形式の仕様書が単に沈黙しているだけでなく、libsidplayfp自身のドライバーも、無関係なCIA／ラスター設定の分岐が最後に読み込んだ値をそのまま保持しているだけで、文書化された値ではありません。これらを0にするという本パッケージ自身の選択は、文書化されていない規約を推測したものではなく、意図的で仕様上中立なデフォルトのままです。詳しくは下記「既知の限界」とコーパスの表を参照してください。

同じオラクルは、既に修正済みの実在する適合性の欠落も発見しました：`Cpu6510`のリードモディファイライト命令（`INC`／`DEC`／`ASL`／`LSR`／`ROL`／`ROR`、および非公式のSLO／RLA／SRE／RRA／DCP／ISCの組み合わせ）には、NMOS 6502が仕様として持つダミー書き込みが欠けていました - 実機では、RMW命令は変更後の値を書き込む前に、未変更の値を一度バスへ書き戻します。1サイクル離れた2回の書き込みであって1回ではありません - 実在するPSID／RSID曲の中には、SIDレジスタへの`INC`／`ASL`を直接使ってフェイクのゲート再トリガーを意図的に利用するものもあります。`Cpu6510`はこれまで2回目の書き込みしか行っていませんでしたが、いまは両方を行い、オラクル自身のサイクル精度のトレースに対して検証済みです。

**この環境が模擬するもの。** `$D400`の1基のSID。CIA 1タイマーAを60Hzの割り込み源として、「上位バイトの書き込みでカウンターも即時ロードされる」という既知の癖ごと。VICはフレームごとに1回のラスター割り込みパルスとして、ファイル形式自身が定めるPAL（19656サイクル）またはNTSC（17045サイクル）周期を使います。さらに実機どおりのバッドラインDMAスティールも備えます：`$D011`自身のYSCROLLの下位3ビットと一致するラスター行`$30`〜`$F7`のうち、DEN（ビット4）が立っている行ごとに1回、VICがバスを43サイクル（`BADLINE_STEAL_CYCLES`）奪い、実際のトリガー地点はその行に入ってから11サイクル目（`VICII_FETCH_CYCLE`）です - どちらも、データシートの丸めた「40サイクル」という数値ではなく、libsidplayfp自身のサイクル精度のVIC-IIコア（ピン留めしたオラクルのリビジョンにおける`c64/VIC_II/mos656x.h`／`.cpp`）自身のBAピンと`startBadline()`を計測器で直接計測したものです。ファイル形式自身が定めるデフォルト環境：PSIDではspeedフラグが0のときのみVICラスター割り込みを有効化し、CIA 1タイマーAは常時稼働ながらspeedフラグが1のときのみ割り込みを有効化。RSIDではCIA 1タイマーAは稼働かつ割り込み有効の状態で開始し、VICラスターは設定だけして無効のままにします（RSID曲は自前のハンドラーを組み込み管理するため）。どちらの場合も`$D011`は`$1B`（DENセット、YSCROLL 3）から始まります - これは、本環境が同梱しない実機のKERNALが、実機上でINITが実行される時点までに必ず残している値であり、libsidplayfp自身の参照ドライバー（`psiddrv.a65`の`vicinit`）も同じ理由で明示的に書き込んでいる値です。バンクレジスタ`$01`は、PSIDではINIT／PLAY呼び出しの直前ごとにファイル形式自身の式で書き込みます（RSIDは自前のハンドラーが入った後は自分で管理）。`playAddress`が0でないPSIDには、`$0334`に小さな環境インストール型トランポリンを用意し、PLAYを呼ぶ前に模擬している両方の割り込み源を確認応答します（どちらが発火しても同じハンドラーに入るため）。`playAddress`が0のPSIDと、すべてのRSIDでは、代わりにINIT中に曲自身がインストールしたハンドラーをそのまま使います。INITが戻った後は、CPUを`$0350`の自己`JMP`アイドルループに置きます。実機が割り込みの間に行っていることと同じで、戻り先番地に何があるか分からないまま実行させることはしません。

**模擬せず、推測もせず名前付きで拒否するもの。** マルチSIDファイル（v3／v4ヘッダーで2基目・3基目のSIDアドレスを指定）。Compute!社のSidplayer MUS形式（フラグビット0） - 組み込みの機械語プレーヤーのみに対応。C64 BASICインタープリタを必要とするRSIDファイル（フラグビット1） - BASICインタープリタは模擬していません。この3つはいずれも、無音のフォールバックではなく名前付きの`PsidFormatError`を投げます。エラーにせず単に含めていないもの（再生される曲で観測可能な違いを生まないため）：CIA 1のタイマーB、TODクロック、シリアルポート。スプライトDMAと、上記のフレームごと1回のIRQパルスおよびバッドラインスティール以外のVIC-IIラスター比較器の挙動すべて（フレーム途中で`$D011`／`$D012`を書き換えてラスター割り込みの対象行を変えることも、スプライト駆動のバス奪取もありません）。バンク切り替えとKERNAL／BASIC ROMイメージ（本パッケージはC64のROMイメージを一切同梱せず、今後も同梱しません（decision 41）。そのため`$01`は式の値を書き込みますが、それを読み戻してメモリのデコードを変えることはありません）。そして、サイクル単位で駆動するSID読み戻し - `$D41B`／`$D41C`（OSC3／ENV3）は、他のすべてのレジスタで`Sid.ts`が既に使っているのと同じフォールバックにより、インポート中にSIDバスへ最後に書き込まれたバイトを返すだけで、発振器やエンベロープカウンターを実際に模擬してはいません。

### オラクル：libsidplayfp

`scores/psid-corpus`は、2本の小さな自作PSIDフィクスチャ（CC0、本チケット自身のもの - HVSCや商用の吸い出しは一切使わない。decision 41）を、ピン留めしたリビジョンでクローン・ビルドしgitignore対象の`.artifacts/`ディレクトリに置いたlibsidplayfpに対して採点します（`native-oracle.mjs`。GPL-2.0-or-later、ベンダリングはしない）。小さな独自実装のロガー（`sidplayfp-harness.cpp`）を、libsidplayfp自身のCPU・CIA・VIC・曲読み込みエンジンへ、その公開`SidConfig::sidEmulation`フックを通して差し込みます - SIDの音声は一切模擬せず、libsidplayfpのソースにも一切パッチを当てません - そして、`psid-import.ts`自身の環境が記録するのと同じ`{cycle, addr, value}`という形で、SIDへのすべての書き込みを正確なクロックサイクルとともに出力します。

- **`convention-probe.sid`**：INITが`A`、`X`、`Y`とPHPで取り出した`P`を、何もしないうちに一度だけ`$D400`〜`$D403`へそのまま格納します - 呼び出し規約そのものを、書き込みストリームとして読み戻すものです。`X`と`Y`は比較そのものから除外されます（`compare.mjs`自身の`ignoreAddrs`）。仕様上未定義のレジスタには採点すべき正解がなく、この2つの書き込みは一致としても相違としてもカウントされず、そこで止まらずに走査は先へ進みます。下記の「INITレジスタ」列ではこれらを「仕様上未定義」と表示します。それ以外の`A`、`P`、そして続くPLAYフェーズ全体は通常どおり採点され、「一致」列にそのまま反映されます。

## 電源投入状態
