# ゲームボーイAPU (`dmg`)

<p align="center">
  <a href="dmg.md">English</a> &bull;
  <a href="dmg_ja.md">日本語</a>

**数値の意味。** 先頭列だけでなく末尾列を見てください。各ボイスのほぼ全区間は、区間ごとの一定シフトでエッジ時刻と値が参照と揃います。矩形波のデューティと速度、上下両方向のエンベロープ、3段階の波形出力、両ビット幅のノイズ系列を確認できます。一致サイクル数が低いのは、音の開始規約が系統的に異なるためです。参照はトリガー直後に最初のステップを出しタイマーを再ロードしませんが、実機は再ロード後1周期待ちます。フレーム時計も分周器のビットでなく時刻ゼロで動き、50%／75%デューティの配列も回転しています。その一定ずれだけで各サイクルが不一致に数えられます。

残りの未対応エッジには、参照にないゾンビエンベロープ、周波数適用が1周期遅いスイープ、直ちに初サンプルを出す波形チャンネルが含まれます。[参照README](../../packages/conform/oracles/gb-snd-emu/README_ja.md)に列挙しています。これらはPan Docsやサイクル単位のROM検査に対するchipvoiceの逸脱ではありません。ROMは成功しています。この参照はROMが検査しない短周期ノイズの形とエンベロープの段階を確認できます。より強い参照は次節で、サイクル精度のコアに同じコーパスをかけます。

**数値の意味。** SameBoyはトリガーされたボイスのタイマーを再ロードし、フレームシーケンサーを分周器のビット12そのもので刻み、デューティ配列もPan Docsの順です。したがってGb_Snd_Emuの一定シフトの原因（独自の256 Hz時計、タイミングのないトリガー、回転したデューティ）はどれも当てはまりません。このシートの以前の版が大きな実機レベルの差と読んでいたものの大半は、実はこの駆動系自身のバグであり、SameBoyのものでも本実装のものでもありませんでした。`main.c`が、すでに順序の整った書き込み列を`qsort`で再ソートしており、同じサイクルを共有する書き込み（コーパスでは、チャンネルの設定レジスタとトリガーが同じサイクルでログされるのが普通です）に対する`qsort`の並び順はC標準では未規定で、glibcとApple libcで実際に異なる結果になっていました。そのため、同一の、無変更の`vendor/apu.c`がコンパイラ間で本当に自分自身と食い違っていたのです（CIがこれを検出しました。gccとclangが同じビルドから異なるトレースを生成していました）。書き込みは元々ログ自身の正しい順序どおりでした（`log.mjs`の`formatLog`はファイルを書き出す前に安定ソートを行い、`main.c`自身の読み込みループも順序が乱れたものは既に拒否します）。したがってこの再ソートは不要であるだけでなく、この駆動系全体で唯一の非決定的な手順でもありました。これを取り除くと（`main.c`参照）コンパイラ間の不一致が解消され、副次的に各scriptログが35〜90 %台から97〜100 %まで上がりました。`script-sweep`と`script-wave`もそうで、このシートの以前の版で実機との不一致に見えていたものは完全にこのバグであり、所見ではありません。両コンパイラで一致するようになった今も残っているのは以下の通りです。ほぼ全ログに軽く触れる実在の狭い起動遅延が1つ、ノイズに固有の、より大きく別個の未解決の差が1つ、そしてゾンビモードの複合ケースです。いずれもPan Docsやblarggの、成功し続けているROMに対するchipvoiceの逸脱ではありません。全てのサイクル・ボイス・値の組は[`corpus/dmg/parity-sameboy.json`](../../packages/conform/corpus/dmg/parity-sameboy.json)にあります。

- **#86（P2-1）以降、`Pulse`も無音で始まるようになり、この差の大半は解消しました。残るのは10サイクルの一定オフセットで、数千サイクルではありません。** #86より前は、`script-envelopes`の最初のノート（サイクル419430）で`本実装`はNR14のトリガービットが立った瞬間に15を返し、SameBoyの対応するエッジはサイクル427399、7969サイクル後でした。`vendor/apu.c`のNR14/NR24トリガー処理は`delay`フィールド（無音からなら`6 + lf_div * ...`、既に鳴っていたなら`4 - lf_div + extra_delay`）をタイマー再ロードに設定し、その最初の自然なティックが来るまでチャンネルを`sample_surpressed`としてマークします。コメントには「NRx4のサウンド開始による音量変化は即座に効くが、再生自体は瞬時ではないため、それ以外の場合はサンプルを更新しない」とあります。`dsp.ts`の波形チャンネルは既にこれと全く同じ挙動をモデル化していましたが（下記「トリガー後の初フェッチが6サイクル遅れる」の行）、`Pulse`はそうなっておらず、トリガーが立った瞬間の現在のデューティ位置を読んでいました。7969サイクルの大半は、`Pulse`が飛ばしていたデューティ1段分ぶんの無音でした。#86は`Pulse`にもPan Docsが言う「最初のデューティの1段までデジタルのゼロを出す」挙動を与え（Pan Docs:「When first starting up a pulse channel, it will _always_ output a (digital) zero」、下記「無音から始まる矩形波」参照）、同じノートの最初のエッジは今サイクル427389に来ます。SameBoyの427399より10サイクル前で、数千サイクル後ではありません。その後のエッジは今も同じサイクル（例えば458751）で完全に一致します。残る10サイクルは`delay`フィールドそのものです。SameBoyの実際のタイマー再ロードはトリガーの書き込みから数サイクル後に来ますが、これは`Pulse`が今持つデューティ1段分の抑制の上に乗る差で、本実装の再ロードは今も書き込みそのもののサイクルに来ます。小さな差です（`script-envelopes` 97.45 %、`script-pulses` 99.82 %、`script-sweep` 99.97 %。#86より前の97.44 %、99.81 %、99.94 %から上昇）。数千サイクルではなく一定10サイクルになりましたが、依然として実在する差であり、P2-1の次の段階に残します。範囲はトリガーごとのこの小さな一定オフセットだけであり、このシートの以前の版が言っていた「トリガーされたすべてのノート」ではありません。
- **長さカウンターは一致しています**：`script-lengths`はコーパス中最良のログです（98.96 %）。channel 3の1946個のエッジは全て完全一致、channel 4は99.00 %で、256 Hz時計と「NRx4書き込み時の追加時計」の癖（[Pan Docs, "Length Timer"](https://gbdev.io/pandocs/Audio_Registers.html#length-timer)、blarggのROM 07）は両者で同じです。channel 1・2に残るずれ（それぞれ99.98 %）は上記と同じ起動遅延が原因で、長さカウンター固有のものではありません。このログはNR52で電源を切ることが一度もないため、電源サイクルをまたぐ保持の検証はどちらの側でも行われていません（結果ではなく、コーパスの穴です）。
- **ノイズLFSRの「トリガー時は無音」という規約は同じで、極性だけが逆です。その長いコールドスタートは実在する差で、上記の矩形波の1エッジ分の遅延とは別の、より大きな差です。** `dsp.ts`はLFSRを`0x7fff`で初期化しビット0を「無音」と読みますが、SameBoyの`prepare_noise_start`は0で初期化しビット0を「オン」と読みます。これは同じ事実を補完的に符号化しているだけで、Pan Docsの「Noise Channel」および`NR43`の幅ビットが持つ2つのフィードバックタップ（ビット14は常時、幅ビットが立っている場合はビット6も追加）は両実装とも同じです。`script-noise`は上記の書き込み順序の修正による影響を受けません（修正前も後も52.11 %：このログの同時のNR41-NR44書き込みは、たまたま両コンパイラで既にファイル順に並んでいました）。コーパス中最大の残存差のままです。`本実装`は最初のノートをサイクル419909で開始しますが、SameBoyの対応するノートはサイクル1887875、1467966サイクル（1ノート分丸ごと）後まで始まらず、その後は両者ともログの残り全体でロックステップを保ちます（154713エッジのうち132099がシフト-8で揃います）。これは実在する未解決の差であり、上記の矩形波の遅延とは独立に、P2-1のもとで調べる価値があります。このシートの以前の版が言っていた同じ原因ではありません。
- **ゾンビモードのエンベロープ書き込みは実際にコーパスで行われており（`script-envelopes`自身の注記にも「a zombie write mid-note」とあります）、単純なケースでは両モデルが一致し、複合ケースでは食い違います。** サイクル20132659で、channel 1が鳴っている最中にNR12が`$A0`から`$A1`へ書き換えられます（periodが0から1、方向は同じ）。`dsp.ts`の`oldPeriod === 0 -> volume++`は書き込みの瞬間に10から11になります。SameBoyの音量も11になります（次の自然なデューティエッジ、サイクル20138149、1デューティ周期以内で確認できます。書き込みのそのサイクルで見えない唯一の理由は、その瞬間channel 1のデューティビットがたまたま低かったためです）。サイクル20552090では、NR12が`$A1`から`$A9`へ書き換えられます（periodは1のままですが、エンベロープの方向が反転します）。`dsp.ts`は3を読み、SameBoyは7を読み、その後もそれぞれ自分の値を保持し、収束しません。`vendor/apu.c`の`nrx2_glitch`に付いた本人のコメントがおそらくの理由を示しています：「pre-CGBモデルでは*一部*が非決定的である。具体的には$x0への書き込みは非決定的に見えるが、$x8は常に期待通りに動く」。DMG-Bでは`nrx2_glitch`が`_nrx2_glitch`を2回、中間値`0xFF`を経由して実行する、文書化されたpre-CGB-D固有の、単純な閉じた式のないモデルです。`dsp.ts`の単純な1段階の式（blargg自身のグリッチの説明に基づく)はそのモデルではなく、この複合ケース（非ゼロのperiodでの方向反転が、既にずれた音量の上に重なる)がまさに両者が分かれる点です。実機のゾンビモード自体、SameBoy自身の言葉で一部非決定的なハードウェア挙動と認められており、これはどちらの側のバグとも言えない、正真正銘の未解決の疑問です。

**無音から始まる矩形波。** 2026-09-27以降（P2-1）、停止中にトリガーされた矩形波は、開始位置のパターンに関係なく、最初のデューティの1段までデジタルのゼロを出します。Pan Docs：「When first starting up a pulse channel, it will _always_ output a (digital) zero.」SameBoyの`apu.c`も同じで、チャンネルを始動する全てのトリガーでサンプルを抑え、最初のtickで解除します。Gb_Snd_Emuはすぐにパターンを鳴らすため、上のベースラインは無音から音が始まる矩形波の行で一致サイクルが減る形で書き直しました。最大5759（`script-sweep`のch1）で、そうした音1つにつき1段分です。P3-4の参照で測ったSameBoyに対しては、同じ変更で矩形波を含む全ログの一致数が増えます。blarggの12本のROMはどちらでも成功し、これを検査するものはありません。

<a id="power-on-state"></a>
## 電源投入状態

`reset()`は起動音を除くブートROM終了後相当です。電源オン、レジスタと波形RAMはゼロ、フレームシーケンサーは最初の時計直前、ノイズは全ビット1です。実ブート音が残すpulse 1設定と左右マスター音量7は、ROM実行前にハーネスが書き込みます。

<a id="history"></a>
## 履歴

- 2026-09-27：無音から始まる矩形波が、最初のデューティの1段までデジタルのゼロを出すように。Pan DocsとSameBoyの通り（P2-1）。Gb_Snd_Emuのベースラインをそれに合わせて書き直し。
