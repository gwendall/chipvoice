# Konami VRC6 (`vrc6`)

<p align="center">
  <a href="vrc6.md">English</a> &bull;
  <a href="vrc6_ja.md">日本語</a>
</p>


NEXT-14の拡張音源チップの最初の1つ(decision 38)：KonamiがNES/Famicomの一部の自社カートリッジに載せたマッパーチップで、16段階のデューティ比テーブルを持つ2つのパルス(2A03の4種の固定デューティとは異なる)と7ビットの鋸歯状波を追加し、それぞれが独自の12ビット周期(2A03自身の11ビットパルスより1ビット広い)を持ち、コンソール自身の5ボイスを置き換えるのではなく、それらと混ざって鳴ります。各節の方法は[CONFORMANCE.md](../CONFORMANCE_ja.md)にあります。

| **状態** | **作業中**：2つの独立した参照実装、Game_Music_Emuの`Nes_Vrc6_Apu`と、2巡目からはMesen 2自身のVRC6音源に対して測定。コーパスは、両参照実装自身の既知の欠落（最初の有効化後は無効化しない、周期が4以下にならない、`$9003`へ書き込まない）を避ける全スクリプトが両方に対して文字通り100 %でゲートし、その欠落のいずれかに触れるスクリプトはMesen 2（3つとも再現する）に対して厳密にゲートする一方、Game_Music_Emuは同じスクリプトをCIをゲートせずに報告するよう分割済み。3巡目は、全ボイスを一度に複数回有効化／無効化する元の8本のコーパスのうち、パルスのみを無効化・再有効化する4本をMesen 2に対して代数的なマッピングで文字通り100 %のゲートへ引き上げ（シフトではなく厳密な写像 - 下記「パルスのマッピング」参照）、鋸歯状波を無効化・再有効化する残り4本は独自の回帰なしベースラインのままです：Game_Music_Emu比で38.1 %、Mesen 2比で90.4 %（3巡目のマッピング前は23.6 %）、ボードが読む区間ごとのシフト許容一致率は105区間中79.0 %。自作のVRC6 NSFプローブが、Game_Music_Emu自身の`Nsf_Emu`プレイヤーを介したNSFエクスポート／再生の往復が正確に一致することを証明済み；ドライバーはまだ届いていない |

<a id="digital-parity"></a>
## デジタル一致率

ハーネスである[`conform`](../../packages/conform)が、2つの独立した参照実装 - [Game_Music_Emu](../../packages/conform/oracles/game-music-emu)の`Nes_Vrc6_Apu`と、2巡目からは[Mesen 2](../../packages/conform/oracles/mesen)自身の同梱VRC6音源 - に対して測定します。2巡目は、各スクリプトが実際に何を検証するかでコーパスを分割しました（理由は`generate-vrc6.mjs`自身のコメントにあります）：

- **`core`**（[`packages/conform/corpus/vrc6/core`](../../packages/conform/corpus/vrc6/core)）：最初の有効化後は無効化しない、周期は4以下にならない、`$9003`へは書き込まない - デューティテーブル、モードビット、音量、周期、オーバーフローを含む鋸歯状波レート、複数ボイスの独立性。**両方**の参照実装に対して文字通り100 %を課します：ここは資料、本コア、そして2つの独立したエミュレーションがサイクル単位で正確に一致する領域です。
- **`edge`**（[`packages/conform/corpus/vrc6/edge`](../../packages/conform/corpus/vrc6/edge)）：無効化／再有効化、`$9003`、極小の周期。Mesen 2はこの3つ（`$9003`、鋸歯状波の無効化時アキュムレーターゼロ化、4以下の周期）すべてを再現するため、これらもMesen 2に対しては厳密にゲートします。Game_Music_Emuはこの3つのどれも再現しないため（下の「数値の意味」参照）、それに対してはこれらのスクリプトは報告のみで、CIをゲートすることはありません - 既知の欠落を、緩めた閾値としてではなく規則として明記しています。
- 元の8本のコーパス（デューティジェネレーターが常時稼働）は全ボイスを一度に複数回の有効化／無効化サイクルにさらし、Mesen 2に対して測定すると2つに分かれます：
  - 4本（`script-duty`、`script-pulse-both`、`script-pulse-enable`、`script-pulse-periods`）はパルスを無効化・再有効化しますが、鋸歯状波が無効化されている間は一切触れません。3巡目が見出したのは、そこでのパルスの不一致はシフトでは埋まらない位相の規約ではなく、厳密な代数的マッピングだということです - 下記「パルスのマッピング」参照 - そのためこの4本は今や`core`や`edge`と同じく、Mesen 2に対して文字通り100 %でゲートします（`check:vrc6-flat-mesen`）。
  - 残り4本（`script-all-three`、`script-saw-enable`、`script-saw-rates`、`script-saw-worked-example`）は鋸歯状波を無効化・再有効化します。ここではMesen 2自身の分周器が無効化中は完全に計数を止めます - 下記「鋸歯状波の分周器と無効化」参照 - これはマッピングが届かない、本質的に別の仕組みです。この4本は両参照実装に対して元の回帰なしベースラインのままです。

マーカーの間の数値はハーネスが生成し（`pnpm --filter chipvoice-conform baseline:vrc6*`、下の表ごとに1スクリプト）、その解釈は手書きです。CIは全コーパスを再実行し、`core`、`edge`対Mesen 2、または`flat-mesen`のスクリプトの一致数が完全一致でなければ、あるいは従来コーパスの一致数がどちらかの参照実装に対するコミット済みベースラインを下回れば失敗します。`packages/conform/test/vrc6-gate.mjs`（`test:unit`の一部として毎pushで実行）は、各厳密ゲートが、コーパスがたまたまそのバグの経路を検証していないから通っているだけではなく、実際に回帰を検出できることを証明します：各ゲートスクリプトの元になっているのと同じ`chip.trace()`／`oracle.trace()`／`compare()`を、コーパスログ自身の書き込みに対して一度（相違があってはならない）、そして1つの書き込みの有効化ビットを反転させたコピーに対してもう一度（相違がなければならない）実行します。対象は`check:vrc6-core`、`check:vrc6-core-mesen`、`check:vrc6-edge-mesen`、`check:vrc6-flat-mesen`のそれぞれです。`check:vrc6-flat-mesen`にはさらに、コーパスを壊せば検出されるという話だけでなく、マッピング自体が効いていることを証明する独立したネガティブテストがあります - 下記「パルスのマッピング」参照。

**数値の意味。** 2巡目は、従来の数値が2種類の問いを同時に背負わなくて済むよう、コーパスを明確に分割しました。上の`core`と`edge`のスクリプトが答えるのは「本コアは資料と一致するか、別々の人が別々のソースから作った2つのエミュレーターで独立に確認できるか」という問いです：Game_Music_Emu自身の3つの既知の欠落のいずれにも触れないスクリプトではサイクル単位で正確に一致し、その3つに触れるスクリプトでもMesen 2に対しては正確に一致します。そして3巡目からは、従来コーパス自身の8本のうち4本もMesen 2に対して文字通り正確に一致します（上の「平坦コーパス」と下の「パルスのマッピング」参照）。従来コーパスの生の見出し数値（Game_Music_Emu比38.1 % - 2巡目の極性修正とコーパス分割の後で35.7 %から上昇、Mesen 2比90.4 % - 3巡目のパルスのマッピングの後で23.6 %から上昇）が答えるのは別の問い、「あるスクリプトが全ボイスを一度に複数回の有効化／無効化サイクルにさらすとどうなるか」であり、Game_Music_Emuに対しては依然としてそのために、このチップに関しては特に過小評価であり、まだ乖離が残る4本についてはMesen 2自身の鋸歯状波についても同様です（下記「鋸歯状波の分周器と無効化」参照）。コーパスはあえて全ボイスを複数回の有効化／無効化サイクルにさらしており（理由は`generate-vrc6.mjs`自身のコメントに書かれています）、Game_Music_Emuの`Nes_Vrc6_Apu` - 直接読んだ`gme/Nes_Vrc6_Apu.cpp`（同梱オラクル内） - は、資料も本コアも行わない、無効化をまたいだ状態凍結を行います。パルスの`run_square`は`volume && !gate && period > 4`が真の間しか16段階の位相を進めません。これはチャンネルが無効化されている間（そこでvolumeが0に強制される）、または「常時オン」モード（`gate`が真）の間は偽になるため、位相は止まった場所で保持され、再有効化後もそこから再開します - 一方nesdev自身の文章（「Eが再びセットされると最初から再開する」）と本コアはどちらも、無効化から有効化への切り替わりのたびにステップ15へリセットします。鋸歯状波の`run_saw`はさらに顕著です。無効化されている間はアキュムレーターにも自身の分周器にも一切触れない分岐を取りますが、nesdevの文章は「アキュムレーターはゼロに強制される」「Eをクリアしても周波数分周器はリセットされない」とはっきり述べており、本コアはそのどちらも文字通り実装しています。オラクルよりwikiページを優先しています（decision 41）。これはどちらの側も知っていると主張する文書化されたハードウェアのリセット値ではなく、本コアが実装のもとにしているwikiページより前に作られた、2005年当時のあるエミュレーター自身の実装に過ぎません。だからこそ`status-data.mjs`自身のボードは、この生の数値ではなく、区間ごとのシフト許容一致率 - 各区間が自分だけの一定シフトを得ればエッジ単位で一致する105区間中79.0 % - を読みます。2A03シートの三角波が、いくつかのログで生の一致率0 %であっても信頼されているのと同じ理由です。

`script-saw-worked-example`は一度も無効化しませんが、その1つの区間は全長にわたって一定の1サイクルシフトに収まります - これは上記の無効化に伴う挙動とは別の、クロッキング順序の規約（どちら側の書き込みが、その着地したサイクルで効くか）であり、ここで測定された中で最小かつ最も機械的な相違です。`script-pulse-periods`自身の最悪の区間（探索で解決できなかった数千サイクル規模のシフト）は、同じソースから読み取れるもう1つのGMEのショートカットと符合します。`run_square`の位相前進ループは、リロードされた周期が4サイクル以下のときは常にスキップされ、これはまさにこのスクリプトの周期0と周期1のケースです - オラクルはナイキストレート付近でトグルを止めますが、実チップおよび本コアは動き続けます。これはソースから読み取ったものであり、エッジ単位で独立に再検証したものではありません。`$9003`（周波数スケーリング／ホールトレジスタ）はここにある全スクリプトで書き込まれますが、オラクル自身のアドレスデコード（`reg_count = 3`）がディスパッチに届く前にそれを落としてしまうため、どちらの方向にも比較可能な信号を与えません。これらはすべて、ソースの該当行とともに[オラクル自身のREADME](../../packages/conform/oracles/game-music-emu/README_ja.md)にまとめてあります。このシートにとっての代償については、下の「既知の差異」を参照してください。

Mesen 2は、上で述べたGame_Music_Emu自身の3つの欠落すべてを、測定し直すのではなくそのソースから独立に確認します：`Vrc6Pulse::Clock`には周期4以下のガードがなく、`Vrc6Saw::WriteReg`の無効化パスはnesdevと本コアの通りにアキュムレーターをゼロにし、レジスタディスパッチのどこも`$9003`を落としません。だからこそ`edge`と`core`はどちらもMesen 2に対して100 %でゲートします（`oracles/mesen-vrc6.mjs`自身のコメントにソースの該当行があります）。2つの参照実装は、補正後にそれぞれ異なる無関係な2つのサイクルオフセット規約に落ち着きます。Game_Music_Emuの鋸歯状波エッジは、そのエッジ自身の時点で有効だった周期を追跡しつつ、chipvoice自身より`period + 1`サイクル遅れて着地します（`saw-worked-example`と`saw-rates`はそれぞれ自身の末尾を`tailPad: 5`と`tailPad: 25`だけ延長し、その遅れたエッジがスクリプト自身の締め切りで切り詰められないようにしています）。Mesen 2のトレース全体は、パルスも鋸歯状波も同様に、レジスターに依存しない一律1サイクル早いところに位置します（`CYCLE_OFFSET = -1`、鋸歯状波の活動が一切ないパルスのみのログで確認済み）。どちらもハードウェアの主張ではありません：どちらもその特定のドライバー自身のキャッチアップ後書き込みのタイミングであり、一度だけ読み取って補正したもので、スクリプトごとに再導出したものではありません。

<a id="the-pulse-mapping"></a>
### パルスのマッピング

3巡目は、平坦コーパスのパルスの不一致をMesen 2に対するシフトの問題としてではなく、両者のカウンターを直接読むことで扱いました。Mesenの`Vrc6Pulse::_step`（`Vrc6Pulse.h`）は0から15まで上向きにラップしながらカウントし（`(_step + 1) & 0x0F`）、無効化中は凍結し、無効化時に0へリセットされ（`WriteReg`の`case 2`）、出力は`_step <= _dutyCycle`です。本コア自身の`step`（`vrc6.ts`）は15から0まで下向きにラップしながらカウントし、同じく無効化中は凍結し、`enabled`の0から1への立ち上がりエッジで15へリセットされ、出力は`step <= duty`です。Mesenのカウンターをs、本コア自身のカウンターをs'と呼ぶと、どの有効化エッジ以降も両者は全く同じサイクルで凍結し、分周器が発火するたびに逆方向へそれぞれ一度だけ進み、その後のあらゆる無効化／再有効化のたびに同じエッジ（sは0へ、s'は15へ）で再アンカーされます。したがってs' = 15 - sは、最初のエッジ以降、周期・デューティ・有効化のどんな書き込み列に対しても成り立ち、デューティを固定した1回の実行だけの話ではありません。本コア自身の条件`s' <= dutyCycle`にs' = 15 - sを代入すると`15 - s <= dutyCycle`、すなわち`s >= 15 - dutyCycle`が得られます - これはMesen自身の`_step`を逆向きに比較したものであり、`Vrc6Pulse::GetVolume()`で変更した1行がまさにこれです（上記の導出をコメントとして引用済み）。これは厳密です：鋸歯状波ではなくパルスを無効化・再有効化する平坦コーパスの4本すべての全ボイス・全サイクルで（`script-duty`、`script-pulse-both`、`script-pulse-enable`、`script-pulse-periods`、上の「平坦コーパス、パルススクリプトのMesen 2比較」参照）、`core`／`edge`には影響しません（依然100 %）：そこではすでにどのスクリプトも有効化区間をまたいでデューティと周期を固定しており、マッピング前後で条件が一致するためです。

単一の定数タイムシフトではこのマッピングを表現できません（鋸歯状波に使った`compare.mjs`自身のシフト探索が、なぜこれを解決できなかったかの理由でもあります）：カウンターの向きが、デューティ窓のどちらの端を分周器自身のラップに固定するかを決めます - 上向きカウンターは立ち上がりエッジをそこに固定し、下向きカウンターは立ち下がりエッジを固定します - そのためトレース全体を時間方向にシフトするとデューティ窓の両端が一緒に動いてしまい、片方だけを動かす必要がある場合には合いません。上記のマッピングは正しい方を動かします。なぜならそれは片方のトレースをもう片方に当てはめたものではなく、両カウンターのリセット不変量そのものから導かれているからです。

Game_Music_Emu自身のパルス（`gme/Nes_Vrc6_Apu.cpp`）も上向きにカウントします - `phase`はインクリメントされ、16でラップし、チャンネルは`phase < duty + 1`の間ハイを読みます。これはMesenの元の（マッピング前の）条件と同じ向きの同じ比較です。本コアに対してではなく参照実装同士を直接比較して測定すると（周期4以下でGame_Music_Emu自身の欠落が比較から外れてしまう箇所を避け、パルスを無効化・再有効化する3本の平坦スクリプトで）：`script-duty` 92.8250 %一致（最初の相違はサイクル18472、Game_Music_Emu 225、Mesen 0、マッピング前のMesenビルド）、`script-pulse-both` 32.4362 %（サイクル17979、Game_Music_Emu 90、Mesen 240）、`script-pulse-periods` 49.1166 %（サイクル17902、Game_Music_Emu 180、Mesen 0）。両方の参照実装が確かに上向きにカウントしており、本コアはあえてnesdevの文章の方に従っています - 「15から0まで下向きに数える16段階を取る。現在のステップが与えられたデューティサイクルD以下のとき、チャンネル音量Vが出力され、それ以外は0となる」（`vrc6.ts`自身の`Vrc6Pulse`のdocコメントに全文引用） - しかし同じ向きに数えることは互いに一致することを意味しません：この2つの参照実装は、ほとんどのサイクルで互いに食い違ったままです。なぜならMesenは無効化のたびに`_step`を固定値（0）へリセットしますが、Game_Music_Emu自身の`phase`（`gme/Nes_Vrc6_Apu.h`）は`reset()`で一度だけ設定され、その後はいかなるレジスタ書き込みや無効化／再有効化でも二度と設定されません - 位相前進ループが止めた場所で凍結し、そこから再開するだけで、マッピングが当てはめるべきアンカーがありません。上記マッピングがGame_Music_Emuには転用できないのも同じ理由です：s' = 15 - sという恒等式は両側が同じエッジで再アンカーされることに依存しますが、Game_Music_Emu側は一切再アンカーされないため、無効化後の位相はその無効化自身の長さの関数であり、単一の代数的代入で吸収できる定数ではありません。このマッピングが決着させる聴感上の違いは、どちらの参照実装に対しても、デューティ幅や周期そのものではありません - 上のどのコーパススクリプトの`edges`／`shift`／`runs`の数値でもすでに正しいままです - 決着するのは、ノート途中でのデューティ変化をまたいでデューティ窓のどちらの端が固定されたままかということ、「常時オン」モードのノート途中の極性、そしてGame_Music_Emuに対しては特に、無効化後の絶対位相だけです。

<a id="the-sawtooths-divider-across-a-disable"></a>
### 鋸歯状波の分周器と無効化

Mesen 2に対して依然として回帰なしベースラインのままの平坦コーパス4本は、いずれも鋸歯状波を無効化・再有効化し、いずれも同じ単一の、出典のはっきりした理由で相違します：Mesenの`Vrc6Saw::Clock()`（`Vrc6Saw.h`）は周波数分周器のタイマーもステップもアキュムレーターも含む本体全体を`if(_enabled)`の内側に置いており、Eがクリアされた瞬間に分周器の計数は止まり、Eが再びセットされた瞬間に止まった場所から再開します。本コア自身の`Vrc6Saw.clockDivider()`（`vrc6.ts`）は`enabled`にかかわらず毎サイクル無条件に呼ばれ、nesdevの文章を文字通りに読んでいます：「Eをクリアしても周波数分周器はリセットされない」を「一時停止するが計数は保持する」ではなく「決して一時停止しない」と読んでいます。`edge/saw-enable.log`（上の厳密ゲート）はこの違いを構造的に回避しています - そこでのあらゆる無効化区間は鋸歯状波自身の分周器の全周期のちょうど整数倍になっており、一時停止して再開する分周器も、止まらず数え続ける分周器も、次の発火に同じタイミングで到達するからです - これは`oracles/mesen/README.md`自身のVRC6の節にもすでに書かれています。平坦コーパスはこの制約を意識して作られていないため、違いが表に出ます：

- `script-saw-enable`：99.2116 %一致、最初の相違はサイクル30426。スクリプト中3回目の無効化／再有効化で、Mesenの分周器はサイクル24368の無効化からサイクル30421の再有効化まで11に凍結されたままです。本コア自身の分周器は同じ区間で数え続けて数サイクル早く0に達し、30426で発火しますが、Mesenは11から再開するためもっと遅く発火します。
- `script-saw-rates`：90.8676 %一致、最初の相違はサイクル29799、別のレートでの同じ仕組みです。
- `script-all-three`：73.4395 %一致（パルスのマッピング前は15.99 % - パルス部分はすでに正確になっています。上記参照）、最初の相違はサイクル757716、サイクル757705の鋸歯状波再有効化（ログの`$B002 = $80`）の11サイクル後 - 新しい仕組みではなく、同じ凍結・再開の仕組みです。
- `script-saw-worked-example`：99.9972 %一致、最初の相違はサイクル35897 - ログ自身の最後から2番目のサイクル（`# cycles: 35898`）で、その後に本物のエッジが着地できるサイクルが残っていません。このスクリプトは鋸歯状波を一度も無効化せず、自身の`edges`の数（8999/9000が正確に一致、1件だけ不一致）が、最後の1つを除く全エッジが両トレースで同じサイクルに着地していることを示しています：固定サイクル数による境界のアーティファクトであり、上記の無効化の仕組みとは無関係で、他の2本のスクリプトの原因とも別物です。

どちらの側も知っていると主張する文書化されたハードウェアのリセット値はここにはありません。上記のパルスのリセット値が0か15かという違いと同様に、それぞれの参照実装自身の実装上の選択であり、推測ではなくそのソースから読み取ったものです。

<a id="nsf-export-and-playback"></a>
## NSFエクスポートと再生

`exportNsf`（`packages/chipvoice/src/nsf.ts`）は、キャプチャのVRC6レジスタ書き込み（`isVrc6Addr`、コアとハーネスが使うのと同じ10個のアドレス）を、2A03の書き込みと同じ方法でエクスポートされたROMへ流し込み、いずれかが現れると拡張音源ヘッダーバイトのビット0を立てます。これによりそのビットを読むプレイヤー（Famitracker、`foobar2000`、その他多く）は、再生前に自身のVRC6拡張音源を有効化すべきだと分かります。プレイヤーのコード自体はもはや`$4000`からの固定オフセットを保持しません。2レジスタページのストア（`STA $4000,Y`）ではVRC6の3つの独立したページ（`$9000`〜`$9003`／`$A000`〜`$A002`／`$B000`〜`$B002`）には届かないため、2A03かVRC6かを問わず、あらゆる書き込みは今やキャプチャが実際に使うレジスタだけを収めたROM内テーブルへのインデックス経由でディスパッチされ、間接ストア（`LDA table,Y`でゼロページポインタに読み込み、`STA (zp),Y`）で解決されます。これは一律に適用されるため、2A03専用ファイルの出力もバイト列は変わりますが挙動は変わりません。これは既存のCIゲート済みの`nsf-export:check`／`nsf-corpus:check`オラクル一式（すべて実在の2A03音源、コマンドストリームとフレーム書き込みの両方で完全一致、変化なし）で影響がないことが証明されています。`capture-nsf.mjs`（このハーネスがエクスポートされたNSFを再生し直すオフライン6502）は、VRC6ビットが立ったファイルを受け付け、その10個のレジスタへの書き込みを、2A03に対してすでに行っているのと同じ方法でイベントとしてルーティングします。自作のラウンドトリップがこれを`packages/chipvoice/test/nsf.mjs`でエンドツーエンドに証明しています（2A03とVRC6が混在した書き込みをエクスポートし、再生してオリジナルのキャプチャとフレーム単位で照合、2A03専用ファイルが課されるのと同じゲートです）。このプロジェクトが見つけたVRC6ファイルはどれも、[`scores/nsf-corpus`](../../scores/nsf-corpus)自身の規約が要求するライセンス（CC0、CC-BY、パブリックドメイン、またはそれに準ずる寛容なもので、出典URLを併記）を満たしていなかったため、2巡目は代わりに自作の`vrc6-probe`を追加しました（CC0、`make-vrc6-probe.mjs`、`scores/psid-corpus/make-fixtures.mjs`が2つのSIDプローブですでに使っているのと同じ、最後の手段としての自作フィクスチャーの流儀）：VRC6拡張ビットを宣言し、毎フレーム3つのオシレーターすべてに書き込む、小さな手作業アセンブルのNSFです。これはこのシートの他の箇所が使うレジスタ単位の`Nes_Vrc6_Apu`オラクルだけでなく、Game_Music_Emu自身の`Nsf_Emu`NSFプレイヤーでも再生され、そのために`native-oracle.py`のパッチに、`gme/Nes_Vrc6_Apu.cpp`内の2つ目の独立したキャプチャ地点を追加する必要がありました（`Nsf_Emu`はVRC6の書き込みを`Nes_Apu.cpp`経由ではなくそこへディスパッチします）。結果は、`scores/nsf-corpus`と`scores/nsf-export`が他のファイルに課しているすべてのゲートを満たします：`nsf-corpus`ではコマンドストリームの完全一致（2700/2700）、`nsf-export`ではコマンドストリームの完全一致（2773/2773）、フレーム書き込みの完全一致（301/301）、そしてエクスポート損失0.0 % - いずれも両コーパスの全2A03ファイルが測定されるのと同じ実プレイヤーに対してです。

<a id="power-on-state"></a>
## 電源投入状態

`reset()`はVRC6の全レジスタをゼロにします：両パルスと鋸歯状波は無効化・無音、`$9003`のホールトビットとスケーリングビットはクリアされます。これは推測による規約です（VRC6の実機もGame_Music_Emu自身のエミュレーションも、実機の電源投入／リセットシーケンスがカートリッジRAMをクリアし、ドライバーが最初の音符の前に全レジスタへ一度書き込むことを経て、同等の内部状態をゼロのまま残します）。VRC6自身のデータシートが述べる文書化された電源投入デフォルト値ではありません - Konami自身の資料は、レジスタが一度書き込まれた後の挙動を記述するのみで、そのリセット値は述べていません。
