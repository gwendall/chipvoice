# Ricoh 2A03 (`2a03`)

The NES and Famicom's sound, as the CPU had it on the same die: two pulses, a
triangle, a noise generator, and a sample channel. The method behind every section

**What the numbers say.** The two pulses are identical to the oracle cycle for
cycle on all three songs: every edge exact, none unmatched, every run aligned at
a shift of zero. So are the sweep-unit mute and its `$4001 = $08` cure, the
`$4003` phase restart, and the downward sweep on both pulses, including pulse 1's
extra minus one. What differs falls into three classes, and none of them is a
chipvoice bug against nesdev; each is a convention of a 2005 oracle that the
documentation has since moved past.

1. **Frame timing.** The oracle's frame steps land two cycles after nesdev's
   7457, 14913, 22371, 29829, which `test/clock.mjs` pins. Anything the frame
   counter drives - an envelope step, a sweep step, a length or linear counter
   running out - happens two cycles later in the oracle, and a pulse whose
   period the sweep changed keeps a phase offset from then on. That is
   `script-envelope`, `script-sweep-up`, the pulse lines of `script-five-step`
   and the tail of `script-length`. A second, modern oracle (P1-13) would settle
   which timing is the hardware's; the test ROMs blargg wrote later say nesdev's.
2. **The triangle's sequencer position.** When its counters reload, the
   oracle steps at once; the hardware waits for the timer's next expiry, and so
   does this core. The oracle also starts on the other of the sequence's two
   zeros. From the first note on, the two sequencers are two steps apart, and
   because the hardware never resets the triangle's position, the offset lasts
   for the whole song: every triangle line reads a few percent identical while
   the dump shows both stepping every `period + 1` cycles through the same
   values, 2030 cycles apart. Every triangle figure in the table is that one
   offset.
3. **Envelope at power-on.** The oracle's `reset()` writes `$4003` to every
   voice, which leaves its envelope start flag set; its first frame clock then
   loads every decay level with 15. A voice put in envelope mode before that has
   decayed sounds at 15 in the oracle and at 0 here, where nesdev says the decay
   level is 0 until a `$4003` write is processed. The scripts start a tenth of a
   second in so that this does not colour them.

The noise is not compared: the oracle's register starts elsewhere, runs with the
inverse polarity and is not clocked exactly while muted, so its bit pattern
cannot match anything. Its rates and sequence lengths are pinned by the formula
tests, and its envelope shares the pulses' code. The DMC is not built.

## Analog stage

Not measured, and no reference unit chosen.

| | |
| --- | --- |
| Profile | `nesdev`: first-order high-pass at 90 Hz and 440 Hz, first-order low-pass at 14 kHz, the values nesdev gives as approximate, and a make-up gain of 2.9. The only profile; `NesOutputStage` takes another |
| Reference unit | none chosen |
| Capture | none |
| Tolerance | not set |
| Maximum band error | not measured |
| Corners measured | not measured |
| Resampling | a box filter over the CPU cycles that make up each output sample; not band-limited |

The mixer is the nesdev non-linear approximation, `95.88 / (8128 / (p1 + p2) + 100)`
for the pulses and `159.79 / (1 / (t/8227 + n/12241 + d/22638) + 100)` for the
rest. A fixed gain of 2.9 follows the filters for headroom. That gain is not
hardware and will be replaced by a calibrated level when a unit is measured.

## Known deviations

| What | Deliberate | Why | Affects |
| --- | --- | --- | --- |
| The DMC is not implemented; the mixer takes 0 for it | no | not built yet | every game in the corpus that uses sampled drums will diverge; the mixer's non-linearity means the other channels' levels are also slightly off whenever the DMC would have been non-zero |
| The frame IRQ is not implemented, and `$4015` cannot be read | yes | there is no CPU to interrupt or to read | `apu_test` cases that read the status register |
| The `$4017` write delay is 3 cycles on one APU phase and 4 on the other, from nesdev, and which phase is which is unverified | no | no oracle yet | at most one cycle on every frame sequence start |
| The triangle powers on at step 15 (output 0); the hardware at step 0 (output 15) | yes | a held 15 at power-on is a DC step through the high-pass filters, a click at the head of every render | the initial state only; see [DECISIONS.md](../DECISIONS.md) |
| `$4014` and `$4016` are ignored, and writes are decoded without the CPU's bus timing | yes | no CPU | none for a driver; a cycle-level oracle comparison may show a one-cycle offset on the write itself |
| Resampling is a box filter per output sample rather than band-limited step synthesis | partly | simple, fast, and the grit is wanted | aliasing on high pulse notes. Parity is measured before it; the analog sheet reports it |
| Output filters are first-order sections at the approximate corners, with no unit named, and a fixed gain of 2.9 | no | no measurement yet | the analog sheet |
| Envelope, sweep and length counters are implemented from the wiki and verified by nothing | no | the driver never uses them | unknown until the corpus and the ROMs run |

## Power-on state

`reset()` is power-on: every unit fresh, `$4015` and `$4017` at zero, nothing
queued. The cycle clock and the filters are left alone - the sample clock did not
stop, and zeroing a filter is a step through it. Power-on: every voice disabled
until `$4015` is written, the LFSR at 1 (as the hardware), the frame counter at
cycle 0 of the 4-step sequence, the triangle at step 15 (deviation above), every
timer at 0.

## History

Newest first.

- 2026-09-04 · Register writes are bytes on `$4000-$4017`, decoded the way the
  chip decodes them. Two things the driver could do before and the hardware
  cannot are gone: a pulse's period high bits now change only through `$4003`,
  which restarts the phase, and `$4001` is written with `$08`, so pulse notes at
  period `$400` and above - G#2 and below - are no longer muted by the sweep
  unit. The 5-step frame sequence and the `$4017` write delay exist. Golden hash
  moved.
- 2026-09-04 · A write lands on the CPU cycle it is stamped with instead of at
  the start of the sample around it. Golden hash moved by the sub-sample shift.
- 2026-09-04 · The triangle holds its last value at note off instead of dropping
  to zero. Click on every bass note gone.
- 2026-09-04 · Half frames on the second and fourth steps of the sequence, not
  the first and third. Inaudible with the shipped driver.
- 2026-09-04 · The noise channel ran at half the hardware rate: the period table
  is in CPU cycles and the timer counted at the APU rate. Every drum was an
  octave dark. Golden hash changed with it.
