# Yamaha YM2151 (OPM) (`ym2151`)

<p align="center">
  <a href="ym2151.md">English</a> &bull;
  <a href="ym2151_ja.md">日本語</a>
</p>


NEXT-16's chip, first half: Yamaha's YM2151, the eight-channel, four-operator
FM synthesiser behind the arcade boards and home computers of the
mid-to-late 1980s (Sharp X68000, many Taito/Konami/Sega/Capcom boards).
`packages/chipvoice/src/chips/ym2151.ts` is Nuked-OPM ported line for line -
the same choice decision 17 made for the YM2612 and Nuked-OPN2 - so the
port's own die-shot-derived source is its oracle. Decision 38 keeps this
out of the studio picker and the arranger for this ticket: a chip, its
harness, a probe corpus and this sheet, not a driver. The YM2610 (OPNB,
NEXT-16's second half) is a separate, later ticket - see
[BACKLOG.md](../BACKLOG.md). The method behind every section is in
[CONFORMANCE.md](../CONFORMANCE.md).

## Digital parity

Measured by [`conform`](../../packages/conform), the harness, against two
independent oracles: [Nuked-OPM](../../packages/conform/oracles/nuked-opm)
(the port's own source, built natively) and
[ymfm](../../packages/conform/oracles/ymfm) (Aaron Giles, independent,
report-only). `generate-ym2151.mjs`'s own comment explains the corpus and
the settling-time convention every script but one follows:

- **`core`** ([`packages/conform/corpus/ym2151/core`](../../packages/conform/corpus/ym2151/core)):
  every algorithm and op1 feedback, detune (DT1/DT2) and multiple (MUL),
  the full envelope (AR/D1R/D2R/RR/D1L/TL), all four LFO waveforms with
  LFRQ/AMD/PMD/AMS/PMS, the noise generator on channel 8 operator 4,
  per-operator key-on, Timer A and CSM, and the stereo L/R enables - one
  script per feature, each held to a literal 100 % against Nuked-OPM.
- **`edge`** ([`packages/conform/corpus/ym2151/edge`](../../packages/conform/corpus/ym2151/edge)):
  key-on while releasing, the TL/AR extremes, DT2 with MUL 0, the test
  register's LFO-reset bit, every NFRQ value, and the two-port write-latch
  settling window itself, deliberately triggered rather than avoided (see
  "Known deviations"). Gated exact against Nuked-OPM on the full corpus.

The numbers between each pair of markers are written by the harness (`pnpm
--filter chipvoice-conform baseline:ym2151-*`, one script per table below);
the reading of them is a person's. CI reruns every corpus and fails if a
`core` or `edge` script's identical count against Nuked-OPM is anything but
exact. [`packages/conform/test/ym2151-gate.mjs`](../../packages/conform/test/ym2151-gate.mjs)
(part of `test:unit`, so it runs on every push) proves the exact gate would
actually catch a regression: it runs the same `chip.trace()`/`oracle.trace()`/`compare()`
the gate script is built from, once on a corpus log's own writes (must not
diverge) and once against a copy with one write's low nibble flipped (must
diverge).

**Where ymfm is the outlier, and why.** See "Known deviations" below for
the specifics; in short, decision 48's precedent (a hardware-verified,
here die-shot-derived, source outranks a second, undocumented-against-hardware
one that merely disagrees) is why ymfm's gate is `--report` only, never
exact, and why a disagreement here is a prompt to look and say which side
is right, not evidence against the port.

## Test ROMs

No machine-readable YM2151 test ROM (a `$6000`-class status byte, a
border-colour or halt-on-done convention) was found, the same conclusion
the VRC6 and Sunsoft 5B sheets reach for their own chips. Real arcade and
X68000 VGM rips of this chip are useful for local measurement but carry no
licence this project's own `scores/nsf-corpus` convention would accept for
a commit (CC0, CC-BY, public domain, or similarly permissive, with a source
URL); they are never committed and stay in a gitignored `.artifacts/`
directory, exactly the "local-only" precedent already set elsewhere in
[CONFORMANCE.md](../CONFORMANCE.md) for other chips' real-world captures.

## Known deviations

| What | Deliberate | Why | Affects |
| --- | --- | --- | --- |
| ymfm's `generate()` is not cycle-exact: it produces one finished sample per call from the register state at that instant, with no notion of where inside a sample a write landed | no, that oracle's own model, not this core's | ymfm is written from public documentation and other emulators' behaviour, tuned against real hardware captures, not derived from a die shot; `oracles/ymfm/main.cpp` batches writes to the sample period they fall in (every 64 log cycles) rather than interleaving them cycle by cycle | every script's timing against ymfm only (`--report`, never gated); no effect against Nuked-OPM, which this core matches exactly, cycle for cycle |
| The address-port write and the data-port write that follows it are only applied once the internal 32-cycle pipeline sweeps back to that register's own channel/slot index; a new address-port write inside that window (up to 64 native cycles) drops the pending one | no, genuine two-port hardware behaviour, not an emulator quirk | found directly: a register write appeared to do nothing until write spacing was widened from 4 to 40 `OPM_Clock()` calls in a debug build; `reg_data_ready = reg_data_ready && !write_a_en` in the vendored `opm.c` is unconditional | every script (`SETTLE`, 4000 native cycles, keeps clear of it); `edge/write-clobber.log` deliberately triggers it instead and is gated exact against Nuked-OPM, which models the same drop |
| Only the YM2151 (`opp = 0`) path of Nuked-OPM is ported; every `chip->opp` branch and `OPP_TLRamp` itself (the YM2164/OPP variant's own TL-ramping and wider register map) are not ported at all | yes, out of scope | decision 51's scope is the YM2151 specifically, the chip NEXT-16 names; the YM2164 is a different, wider-register-map chip this project has no host for | nothing measured here; `ym2151.ts` has no YM2164 code path to diverge from anything |
| The YM2610 (OPNB), NEXT-16's own second half, is not part of this change | yes, out of scope, tracked separately | the YM2610 adds ADPCM-A/ADPCM-B sample playback entirely absent from the YM2151, a substantially different core requiring its own oracle work and probe corpus | nothing on this sheet; see [BACKLOG.md](../BACKLOG.md) for its own ticket |
| No per-channel output tap (unlike `Ym2612`'s `ch_out`) | yes, matches the hardware | the real YM2151 has no per-channel pin - Nuked-OPM sums all eight channels into one shared stereo accumulator internally, and only the two DAC outputs ever leave the die; adding one anyway would require duplicating Nuked-OPM's internal `fm_algorithm` routing table a second time in the C oracle driver, a synchronisation risk for no real output | the harness compares two voices, `l` and `r`, never eight or ten |
| MAME's `ym2151.cpp` was read for cross-reference (register semantics, CSM/timer behaviour) but never vendored or copied | yes | GPL; decision 41 restricts a GPL reference to one actually built and run as an oracle, and two oracles already disagree by a documented, sourced amount | nothing in `ym2151.ts`, `opm.c` or ymfm's vendored files traces to MAME |

## Power-on state

`reset()` replicates `OPM_Reset`'s own bootstrap exactly: every field zeroed
by reflection, `setIC(1)`, 2048 `clock()` calls (32 x 64, one full pipeline
sweep at every one of the 64 slot/channel-indexed internal states), then
`setIC(0)` - the same sequence real hardware's IC (initial clear) pin drives
the chip through, not an instantaneous field reset. `dac_output` is silent
(`[0, 0]`) once that sequence completes, since no register has ever been
written.

## History

- 2026-09-28 (NEXT-16, first half): `Ym2151`, ported line for line from
  Nuked-OPM (decision 51), following the YM2612/Nuked-OPN2 precedent
  (decision 17). Two oracles: Nuked-OPM (die-shot-derived, exact gate) and
  ymfm (Aaron Giles, BSD-3-Clause, independent, report-only). A self-authored
  CC0 probe corpus (`.vgm` files, decoded through a new `ym2151` branch of
  `packages/conform/src/vgm.mjs`'s VGM importer, VGM command `0x54`) covers
  every core-scope feature plus edge cases, including the two-port
  write-latch settling window found and documented during this ticket. No
  driver or arranger role yet (decision 38); API-reachable only. The YM2610
  (NEXT-16's second half) is deferred to its own, later ticket.
