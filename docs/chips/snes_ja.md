# SNES：S-DSP (`snes`)

<p align="center">
  <a href="snes.md">English</a> &bull;
  <a href="snes_ja.md">日本語</a>
</p>


スーパーファミコンの音源S-DSPは、ADSRとGAINエンベロープ付き8サンプルボイス、ガウス補間、ピッチ変調、ノイズ、8タップFIR付きエコーを備えます。SPC700と共有する64 KBからBRRサンプルを再生します。各節の方法は[CONFORMANCE.md](../CONFORMANCE_ja.md)にあります。

| | |
| --- | --- |
| **機種** | Super Nintendo、Super Famicom（SPC700クロック1024000 Hz、32クロックごとに1サンプル、32000 Hz） |
| **状態** | **作業中**：DSP出力はsnes_spcと一致、ドライバーは全役割を再生、`.spc`ファイルは`importSpc`で再生可能、アナログ段は未測定 |
| **コア** | snes_spcのSPC_DSPを逐行移植（`packages/chipvoice/src/chips/snes/sdsp.ts`） |
| **コアのライセンス** | `sdsp.ts`はsnes_spc由来のLGPL 2.1。独自コードはMIT。パッケージは両ライセンスを表示 |
| **更新日** | 2026-09-27、手動および`conform`による生成 |

<a id="digital-parity"></a>
## デジタル一致率

[`conform`](../../packages/conform)で、[`snes_spc`](../../packages/conform/oracles/snes-spc)とDSP出力ストリームを比較します。比較対象はDACへ渡す左右の16ビット値です。[コーパス](../../packages/conform/corpus/snes)のドライバー経由2曲と4スクリプトを使います。マーカー内はハーネスが生成し（`pnpm --filter chipvoice-conform baseline:snes`）、解釈は手書きです。CIは一致数がコミット済み基準を下回ると失敗します。

**数値の意味。** このチップではデジタル出力がDACに渡す出力そのものです。ADSRと全GAINモード、複数レートの音高とノイズ、ピッチ変調、2種類のFIRを通す各遅延／帰還量のエコー、ドライバーバンクとバーストのBRR復号を比較し、移植初回から全ログで左右ともサンプル単位に一致しました。その後、キットのハイハットをDSP自身のノイズへ移した際に4番目のスクリプトを追加し、2ボイスが同じノイズを同時に共有する場合、キーオン時だけでなく保持中の音符でノイズ時計を変える場合、`FLG`のリセットとミュートのビットをノイズ経路の有効なボイスに掛ける場合を検証しましたが、これもsnes_spcと一致しました。初回に見つかった問題はチップではなくプログラム側で、参照実装も同じビットを出しました。

実機キャプチャ由来の起動状態には注意点が2つあります。ESA位置から始まる28 KBのエコーバッファは、旧遅延が尽きて新EDLを読むまでRAM末尾を折り返してサンプル領域に書き込みます。また一部ボイスがキーオン済みで、停止したノイズ時計からエンベロープに従って増える定数が出ます。IPL ROMと同様に全ボイスを停止し、エコー書き込みを無効にして旧遅延を待つ処理を、ドライバー、スクリプト、数式テストへ入れました。

<a id="spc-playback"></a>
## SPC再生

`importSpc`（`packages/chipvoice/src/spc-import.ts`）は`.spc`ファイル
（SPC700とS-DSPを凍結したスナップショット、SNES自身の音楽形式）を、この
パッケージ自作のS-SMP（`ssmp.ts`）とSPC700（`spc700.ts`）で再生します。
これらはfullsnes、AnomieのSPC700・S-DSPドキュメント、SNES開発者wikiの
`.spc`/ID666レイアウトから書き、snes_spc自身のCPUからは一切ポートして
いません。CPUレジスター、64 KBのARAM、128個のDSPレジスターすべてを
正確に復元し、存在すればID666タグ（タイトル、ゲーム名、アーティスト、
長さ）を読み、壊れたファイルや誤認識したファイルは明示的に拒否します。
関数とそのオプションはパッケージのREADMEを参照してください。

[`check:spc`](../../packages/conform/src/spc/check.mjs)で、`play-spc` -
`main.cpp`が既に使っている同じ蓄積済みsnes_spcから作った、blargg自身の
実SPC700（`SPC_CPU.h`）- と比較して測定します。ただし今度はCPUを駆動する
のであって、DSPだけではありません。DSP自体は既にsnes_spcと1行単位で
一致しているため（上の「デジタル一致率」参照）、ここで見つかる相違は
新CPU、そのタイマー、またはスナップショット復元のいずれかしかあり
得ません。比較するのは2つです。CPUが送るDSPレジスター書き込みの
並び（レジスターと値、順序どおり - これが合否の基準。サイクル番号は
併記しますが等値を求めません。blarggのCPUは命令全体を終えた時点の
サイクルで書き込みに刻印し、このパッケージ自身は書き込み自身のバス
アクセスのサイクルで刻印するという、固定のラベル付けの違いが
`spc700.ts`と`check.mjs`に記載されています）。もう一つは出力サンプルで、
「デジタル一致率」と同じ方法で比較します。コーパスは
`packages/conform/corpus/snes/spc`（再配布可能なファイルのみ、現時点では
自作 - READMEを参照）。ローカルのgitignore対象ディレクトリに他のファイルを
置いて個人的にテストでき、CIはそれに依存しません。

<a id="spc-export"></a>
## SPC書き出し

`exportSpc`（`packages/chipvoice/src/spc-export.ts`）は`importSpc`の逆方向です。SNES曲のレジスター書き込みキャプチャ（`recordSong`または`PerformancePlan`の`events`/`cycles`/`memory`、`toVgm`と同じ形）を、chipvoiceのランタイムなしでどのSPCプレイヤーでも、実機でも再生できる標準的な`.spc`ファイルへ凍結します。ARAM自体に自作の小さなSPC700プレイヤープログラム（`packages/chipvoice/src/chips/snes/spc-player.ts`、AnomieのSPC700ドキュメントとfullsnesから手書きでアセンブルし、MITライセンス、他チップの資産と同じパッケージビルドでコミット済みTSソースから生成 - 不透明なバイナリではない）を書き込むためです。

`spc-import.ts`も読む、固定オフセットのヘッダー／DSPダンプ／エキストラRAM構造の中で、64 KBのARAMに入るものは：

- プレイヤー本体（固定アドレス`$0200`）。
- 圧縮されたサンプルディレクトリと、それが指すBRRデータ：曲中でKON書き込みが実際に参照したサンプルだけを、キャプチャのメモリーから一度だけコピーし、ループ点を引き継ぎます。ディレクトリのエントリーも、各SRCN書き込みとドライバー自身のDIR書き込みが指すページも、この圧縮テーブル一つに書き換えます - キャプチャのドライバーは同一ティックで本物の値の直前に紛れのSRCN値を書くことが（実際に）あり、KONは一度もそれを使わないのに、そのままではメモリー上の何にも使われないスロットを読む、根拠のないエントリーになってしまいます。
- 書き込み列：キャプチャが行った全ての`$F2`/`$F3`ペアを、ティック差分・レジスター・値として記録します。同一ティックの連続書き込みは差分バイト1個を共有し、`$FE count (reg value)*count`のバーストとしてまとめられます。さらに、あるグループの並びが以前の並び（同じ和音の再トリガー、同じ楽器のエンベロープの再生）を繰り返す場合は、グループ化した書き込みに対する貪欲なLZ77式のマッチで見つけた、すでに書き出し済みのストリームバイトを指す`$FD`後方参照として記録でき、プレイヤー自身のコピーループでデコードされるため、曲ごとのロジックでアセンブル済みプログラムを太らせません。1ティックはタイマー0自身の周期、SPC700の1024000 Hzクロックに対し`TIMER_TARGET=8`、1000 Hz、1024サイクルです。書き込みの元のサイクル値は最も近いティックに丸められ、その目標は書き出し中にアセンブル済みプレイヤーを実際に*シミュレート*（もう一つのスクラッチSPC700で）することで追いかけるため、待機ループとディスパッチ自身の実コストが見積もりでなく正確に反映されます - 書き込み自体は、丸めだけが約束する半ティックではなく、明記された小さな範囲のティック数に収まります（figureと理由は`spc-export.ts`自身のドキュメントコメントと`packages/chipvoice/test/spc-export.mjs`を参照）。
- 曲のループ点。ゲーム自身のトラックと同じように、再生は永遠にループします。`.spc`ファイルは通常そう作られています。

エコーバッファー（`ESA`/`EDL`）はDSP自身の判断でこの同じARAMに書き込みます。エコー書き込みが有効な間、キャプチャ自身のレジスター書き込みがいつ指しても構いません。`exportSpc`はキャプチャが`ESA`、`EDL`、`FLG`に与える全ての値を追跡し、そのウィンドウがプレイヤー、ディレクトリ、サンプル、書き込み列、またはIPL ROMの予約領域（`$FFC0`-`$FFFF`）に重なりうるファイルの生成を拒否します - `SpcExportSizeError`で、切り詰めや静かな破損ではなく。同じエラーは、`measured`と`limit`を添えて、単純な場合もカバーします：プレイヤー、ディレクトリ、サンプル、書き込み列を合わせても`$FFC0`未満に収まらない曲です。リポジトリの公開済みSNESアレンジ3曲のうち`sonic`はこれに実際に当たるほど大きく測定されます（このドライバーの音符密度と楽器数で数分間のSNES版、書き込み列自身の後方参照圧縮を経てもなお~64 KBの予算を超過）。`mario`と`zelda`はどちらも収まります。まだ`scores/`にSNESネイティブの曲はなく（`native-sources.mjs`はNESとメガドライブのソースのみ）測定対象にできません - できたときはこのコーパスに加わります。

[`check:spc-export`](../../packages/conform/src/spc/check-export.mjs)で、リポジトリ自身の公開済みSNESアレンジに対して、曲ごとに2通り測定します：本実装自身のラウンドトリップ（`importSpc(exportSpc(...))`をこのパッケージ自身のSPC700で実行し、元になったプランの直接レンダリングと比較 - リスナーが実際にファイルから聞く音声）と、実参照実装（同じファイルを`play-spc`、blarggのSPC700で再生、上の`check:spc`と全く同じ方法）。

どちらもDSP書き込み列を比較します：レジスター、値、順序を厳密な一致で判定します。参照実装側はさらに書き込みの*サイクル*も、単一の、名前を与え根拠を示した一つのオフセット（`T0_STAGE1_PERIOD`）まで厳密に判定します。blargg自身が蓄積したsnes_spcには、スナップショット読み込み時に一度だけ生じる「幻の周期」という遅延タイマーモデル特有のクセがあります（`next_time`を1にリセットすることと、経過周期数の式にある無条件の`+1`が組み合わさったもの）。これにより、最初の実タイマー刻み以降の全ての書き込みが、タイマー0の128サイクルのプリスケーラ周期ちょうど1回分、本実装より先行します - blargg自身の参照実装にある既知の単純化であり、どちらの側のバグでもなく、これまで無視されていたものを今は名前を付けて厳密に合否判定します（`check-export.mjs`の`compareOracleWrites`のドキュメントコメントを参照）。ラウンドトリップはさらにタイミングでも合否判定します：各書き込みの実際のサイクルと、`exportSpc`が丸めた先のティックとの最大のずれを、3ティックを上限として、これらと同じ実際の曲で直接測定します（`packages/chipvoice/test/spc-export.mjs`がその余裕の導出元です）。

出力サンプルは2通りで比較します：短いウィンドウでのボイス別RMSエンベロープ相関（合否判定、下の`ENVELOPE_MATCH_THRESHOLD`）、そして参照実装側では音符単位のタイミング一致度（合否判定、`NOTE_TIMING_ALIGNMENT_THRESHOLD`）- 各音符に自分自身の一定シフトを一度与えたときに、その音符のステップが正しい相対サイクルに乗る割合で、相関ではなく本当に厳密な基準です。どちらの側も生のサイクル完全一致サンプル比較では合否判定しません（併記のみ）：自分のティックに正しく丸められた書き込みでも、量子化なしのレンダリングに対してS-DSP自身のオーディオレート波形の位相がずれ、位相だけで同一の音の2つのコピーをほとんど別物と採点してしまうためです。参照実装側では、この差はもはや説明のつかない「位相」だけではありません - 上記の幻の周期オフセットを補正してもなお、このコーパスでの生のサイクル完全一致サンプルは29-40%にしか上がりません。これは、音符相対の*タイミング*は92-97%の割合で一致する一方、音符内の正確なサンプル値はビット単位ではほとんど一致しないためです（S-DSPのコア自体はblargg自身のものを直接ポートしたものなので、両者が計算する内容自体は分岐しません。分岐するのは、絶え間なく変化していくカオス的なパイプラインの種となる、ほんの数サイクルの書き込みタイミングの差です）。音符タイミングの方が、代わりに成立する、より厳密で本当に正確な基準です。詳しい理由と測定値は`check-export.mjs`の`envelopeMatch`、`compareOracleWrites`、`noteTimingAlignment`のドキュメントコメントを参照してください。実際のバグが同じ測定に残す痕跡も含まれています（このファイル自身の履歴で、2件見つけて直したときに使用）。

## ドライバーの対応範囲

`packages/chipvoice/src/chips/snes/driver.ts`の`SnesDriver`を`test/snes-driver.mjs`で検査します。リードは0、和音は1/4/5（拡張時1/4/5/6/7）、ベースは2、打楽器は3です。5音を超える和音は警告付きでアルペジオへ戻します。和音の振幅予算を音数で分け、控えめなステレオ配置を使います。

| ボイス | 使用する機能 | 使用しない機能 |
| --- | --- | --- |

| v3 | バンクのワンショットドラムを`$1000`で再生、フレームごとの音量。キットのハイハットは`NON`経由でDSP自身のノイズへ、電源投入時の最初の`FLG`書き込みが設定する時計で再生 | 保持中の音符でノイズ時計を変える操作（コーパススクリプトでは検証するが、キット自体は行わない） |

<a id="known-deviations"></a>
## 既知の差異

| 内容 | 意図的か | 理由 | 影響 |
| --- | --- | --- | --- |
| `$F3`書き込みは指定クロックの前に届き、同一クロックの複数書き込みは順序を維持 | はい | SPC700はDSPクロック間で書き込み、参照側も同じ規約 | 最大1クロックの到着時刻 |
| ノートオフはKOFFではなく各ボイスのGAIN | はい | KOFFは8ボイス共有。時間順でない予約では状態を保持できず、GAINはボイス固有 | 線形ではなく約8 msの指数減衰 |
| バンクは録音ではなく独自合成と符号化 | はい | チップではなくアレンジャーの楽器 | 意図の音色。チップの動作は変えない |
| `NON`は打楽器ボイスのビットだけを持つ形で丸ごと書き込み、ノイズ時計（`FLG`下位5ビット）は電源投入時の最初の`FLG`書き込みで設定し、その後は別の値へ書き換えない | はい | `NON`とノイズ時計はいずれも全ボイス共有の1レジスタ。`notes: "period"`を持つ打楽器ボイスのChipSpecだけが`noiseMode`を持つため、2つ目のノイズボイスを許すドライバーは他ボイスのビットを上書きせず追跡する必要があり、異なる時計を求める複数ボイスのどれを選ぶかも必要になる | 打楽器ボイス以外がノイズを共有する将来の拡張はKOFFと同様の扱いが必要で、現状のままでは拡張できない。今のところこの状況は生じない |

<a id="power-on-state"></a>
## 電源投入状態

`reset()`はsnes_spcの状態です。実SPCから取得したレジスタ、一部キーオン／ノイズ割り当て、28 KBエコー、ノイズレジスタ`$4000`、ゼロのカウンターを使います。ドライバーはエコー書き込みと出力を無効化し（読み取りも最初はサンプルRAMへ折り返し得る）、全ボイスをオフにし、ディレクトリ、音量、エコー、各エンベロープを設定してKOFFを解除し、起動バッファが折り返した0.25秒後にエコー書き込みと出力を有効にします。最初の書き込み、つまりエコー書き込みを無効化するその書き込みが、ノイズ時計（`FLG`下位5ビット）も最速レートに設定します。曲自身の時刻ゼロから音符が始まり得るため、エコーバッファの安定を待たずに時計を有効にする必要があるからです。後段のエコー再開の書き込みは同じ時計を繰り返すだけで、初めて設定するわけではありません。ノイズへ回した全ボイスが共有するこの時計は、その後は別の値へ書き換えません。

工場出荷バンクは57,344からのエコーバッファより下の21,472バイトを使います。生成とBRR符号化はビルド時です。音量を`$1f`に制限し、飽和加算前に余裕を残します。任意の8ボイス効果音や直接レジスタ書き込みまで保証しません。[パレットの受け入れと測定](../SNES-PALETTE_ja.md)を参照してください。
