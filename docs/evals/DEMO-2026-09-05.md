no merge or production deployment. Scope is [DEMO.md](../DEMO.md), slices A–C.
Live recording, variations, MIDI and stems remain the subsequent slice.

The CI-discovered captured-log scheduling regression and its architectural
correction are covered by the [2026-09-06 follow-up](SCHEDULING-2026-09-06.md).
Its mixer, packaging and Chromium results supplement this initial evaluation.

## What changed

The page is a playable five-machine console with three composed cartridges,
four role lanes, four arcade effects, mute/solo, note/drum editing, timbre
choices, audition keys, undo/redo and draft recovery. Sharing preserves every
pattern, order entry, chord shape, intent and target machine. Publications and
draft links are distinct. The code panel produces a runnable example and a
stereo WAV from a worker.

The machine marks are local SVGs from HVR88's Monochrome Gaming Logos collection,
with provenance and attribution in `apps/web/public/machines/README.md` and the
footer. Multi-tap was inspected first; its logos use a ScreenScraper proxy.

## Visual inspection

The desktop and 390×844 touch-emulated layouts were inspected from actual
production-build screenshots. All five machine controls, Play and the four
arcade pads are visible in the first mobile screen. Note editing uses a
horizontally scrollable grid rather than compressing sixteen touch targets.
The grid includes existing preset pitches outside the audition octave. A frame
from the recorded desktop session was also inspected: C64 correctly marks both
chords and drums when an effect borrows their shared third voice.

## Functional and audio checks

- `pnpm build`, `pnpm typecheck` and the complete package unit suite passed.
- Production API tests ran against a disposable SQLite database, including
  validation, publication/fork, deterministic renders, ID3 and share metadata.
- Chromium, Firefox and Playwright WebKit desktop/touch-emulated journeys passed: explicit audio
  start; measured audio on five machines; switching and Stop; effect ownership;
  keyboard edits; undo/redo; incomplete text; draft recovery; complete draft-link
  round trip; publication reload and title-only fork; stereo worker export;
  copied JavaScript built with the local package and played in another page.
- Chromium additionally dispatched a native touch scroll through the editor
  and verified that the stored score remained unchanged.
- The downloaded WAV was byte-identical to `toWav(renderSong(arrange(score)))`
  with the same target and stereo option. ffprobe identified PCM16, 44.1 kHz,
  two channels, duration 6.667 seconds for this edited test score.
- All five reference corpus checks passed their committed baselines. MD, SNES
  and C64 were identical over their trusted corpus outputs. NES/GB retained
  their documented reference differences; this is not physical-hardware parity.
- A nonexistent conformance baseline exits 1 before running the corpus.

Measured live output in one Chromium run (short samples from different musical
positions; **not** a loudness comparison or performance benchmark):

## Defects found and repaired during evaluation

The two-axis review found six functional issues: published-draft reload loss,
hidden high notes, stale display positions when replacing scores, obsolete
async chip creation, canceled patch/sample initialization and music silencing
a delayed effect. The follow-up review caught a delayed SFX replacement losing
its preceding interval and a chord-shape offset after seeking past a cut.
All were corrected; focused transport and browser regressions cover them.
The conflicting immutable-cache decision was explicitly superseded.

Transport tests observe digital register state and rendered samples, including
Stop, overlapping/delayed effects, held-note recovery and the first note after
cancellation. All five cores produce identical audio with 128- and
4096-sample host blocks. That test exposed consumed MD/SNES writes being replayed
on incremental scheduling. Fixing it intentionally changes their two song
goldens, while raw corpus parity remains unchanged; NES/GB/C64 goldens did not
move. Decision 22 records why.

A source-level performance issue was also removed: rebuilding the SNES encoder
recompiled its constant BRR sample bank. The bank is now compiled once, with
copies supplied at the memory boundary. No numerical speedup is claimed.

## Explicit follow-ups

The host was heavily loaded during evaluation, as reported by the user. Browser
timings, first-sound times and intermittent missed transient observations here
must not be used as a responsiveness baseline. Browser suites were serialized
for the final runs. A mutation observer records transient voice ownership rather
than assuming that the test runner returns during a 300 ms effect.

Real Safari and a physical phone remain to be checked (audio unlock, interruption,
scroll/pinch and reduced motion). Playwright WebKit is a separate engine check,
not a claim about an actual iPhone. Human usability sessions and comparative
latency/CPU measurements await a representative device. These do not block
preparing the PR; the user explicitly requested no merge.

NES/GB ROM and mixer checks remain in CI; the local all-checks command was stopped
to reduce host load after all five corpus checks completed. No ROM/mixer success
is claimed for this local evaluation. Account identity, render-request caching,
range diagnostics and versioned migrations remain explicit audit follow-ups.

CI now cancels obsolete PR revisions, reuses the Next build cache, and runs web
qualification independently of the silicon/ROM suite. The remote chipvoice main
was fetched and unchanged; no Daemon/Moshi CI changes were available in this repo,
so no cross-project reuse is claimed.
