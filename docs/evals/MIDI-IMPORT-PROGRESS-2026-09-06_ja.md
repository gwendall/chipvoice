報告されたインポートは成功していましたが、82.5秒の全アレンジをレンダリングする間、待機状態を説明していませんでした。タイトルとStop意図だけを表示していました。別の文字デコード問題で、原典の`Éclaté`というトラック名も文字化けしていました。

<a id="reproduction-and-test-gap"></a>
## 再現とテストの不足

ローカルの`Musha_Aleste-Theme.mid`は25,427バイト、7パート、2,078音符です。ブラウザは即座に受理してタイトルを更新しましたが、ワーカー処理中の音声は無音でした。新しい長時間インポートE2Eは、名前付き準備表示のない本番版で失敗しました。文字デコード回帰も、結果が`Éclaté`でないことで失敗しました。

以前は2秒・3音符をインポートして見出しを待つだけでした。新検査は進捗、実際のレンダリング／デコード完了、音声ダウンロードを待ち、Playを再度押さずに音を測ります。CIには生成した82.5秒MIDIを使い、任意の`MIDI_FILE`で個人ファイルをコミットせず検査できます。

<a id="fix"></a>
## 修正

- UTF-8を厳密に読み、不正なら通知付きWindows-1252フォールバックを使います。元ラベルを保持します。`Éclaté`は楽器名ではなく原典メタデータです。同名パートはチャンネル番号で区別します。
- SDKはオフラインブロック後に完了フレーム比を通知します。進捗の単調増加とコールバック有無でのPCM同一性を検証します。
- ワーカーは計画／レンダリング／符号化を通知し、整数%ごとに最大1メッセージに抑えます。UIはファイル名、機種、段階、実進捗、経過時間、再生意図を表示し、古い通知を新選択へ適用しません。
- 時間未確定で`0.0 SEC`を表示せず、暫定省略数を最終結果のように見せません。
- 処理完了までStopの意図を守り、置換準備中は既存音声を続けます。

機能上の音声測定であり、音色の忠実度や速度の得点ではありません。ホストは混雑しており壁時計時間はベンチマークに使いません。既存12ミックスの公開評価も更新SDKを検証し、前スナップショットと比較します。

再現方法は[ワークフロー](../../scores/arrangements/README_ja.md#long-midi-import-regression)。画像、動画、JSONは`.artifacts/midi-import/e2e/`にあり、CIでも保存します。

<a id="review"></a>
## レビュー

両軸で本番コードの重大な問題は残りませんでした。設定可能なE2Eでは、初期機種切り替えがインポートをキャンセルする問題と、外部ファイルにも生成fixture専用のトラック名を要求する問題を発見しました。機種選択をアップロード前に行い、専用名は生成入力だけで検査します。Game Boyから始める実ファイル経路と既存アレンジ検査が最終ビルドで成功しました。

![デスクトップのMIDI準備表示](midi-import-loading-desktop.png)
![携帯のMIDI準備表示](midi-import-loading-mobile.png)

最終確認では全12ミックスのWAV／FLACが0.15.0とバイト単位で同じでした。全PCM再現性、有限でクリップしない出力、SNES内部余裕、原典／トランザクション、公開識別が成功しました。生成長時間MIDI E2EもCI追加前にローカル成功しました。

最初のPR CIでは、コピーした実例の既存テストに競合がありました。Nextページのbodyを消して例を挿入する間にReactがhydrateし、例のボタンの代わりにプレイグラウンドが復元されていました。同一originの独立HTMLへ変更し、実例のビルドと実測音声を引き続き要求します。
