# 適合性：チップをどう検証するか

<p align="center">
  <a href="CONFORMANCE.md">English</a> &bull;
  <a href="CONFORMANCE_ja.md">日本語</a>
</p>


chipvoiceの「実機のように鳴る」という主張を、形容詞でなく数字を生む方法で試します。全チップ共通の方法なので、SNESとNESのシートは同じように読め、「完了」も同じ意味になります。

<a id="what-the-machine-means"></a>
## 「実機」の意味

音源には2段階があり、100%を定義できるのは片方だけです。

**デジタルコア**は同期回路です。指定クロックでのレジスター書込列に対し、正しい出力列はサイクルごとに一意です。有限状態機械なので「同一か」には機械的な答えがあります。デューティー列、シフトレジスター、エンベロープ、FMオペレーター、サンプル補間に音の個性があります。

**アナログ段**はDAC以降のすべてです。アナログの混合曲線、出力フィルター、変調器、許容差のあるコンデンサー。同型の実機2台も一致しません。フロントローディングNES、トップローダー、ファミコン、AVファミコンではコーナー周波数が違い、6581フィルターは個体ごとに変わります。唯一の真値がないので、目標は*参照個体*と*許容差*です。

デジタルは**ビットごと**、アナログは**名前を明記した個体に対するdB**で比較します。シートの「100%」はデジタルコアを意味し、残りには個体とdBを記載します。

もう1つ、*決定的*、つまり同じ入力で同じバイトが出ることは、*正しい*こととは違います。ある版のノイズは、決定的に1オクターブ低く鳴っていました。決定性は検証を可能にし、正しさにはオラクル、すなわち参照基準が必要です。

<a id="oracles"></a>
## 参照基準

強い順です。利用できる最も強いものを使い、次の段を早いバグ発見に使います。

| 順位 | 参照基準 | 証明するもの | 費用 |
| --- | --- | --- | --- |
| 1 | ダイから抽出したネットリストのシミュレーション | トランジスター単位の真値 | 実時間の数千倍遅い。試験実行器でなく最終判定用 |
| 2 | 実チップのデジタル出力ピンのロジック取得 | 1個体の真値 | デジタルピンと測定機材が必要 |
| 3 | 1または2で検証された参照エミュレーター | 現行の最良実装との同等性 | 安価。大半の作業をここで行う |
| 4 | コミュニティのテストROM | すでに見つかった境界例 | 実行CPUが必要 |
| 5 | データシートの数式 | 速度、周期、列長 | ほぼ無料。基本的な誤りを捕らえる |

チップごとの参照：

| チップ | 順位1または2 | 順位3 | 順位4 |
| --- | --- | --- | --- |
| Ricoh 2A03 | ネットリストのVisual2A03 | Nes_Snd_Emu（blargg）、Mesen | blarggの`apu_test`、`apu_mixer`、`apu_reset`など |
| Game Boy DMG | | Gb_Snd_Emu（blargg）を使用中。SameBoyは今後 | 専用SM83で`dmg_sound`の12/12。CGB対応後に`cgb_sound` |
| YM2612、YM3438 | デジタル出力のロジック取得が存在し、Nuked-OPN2はダイ由来 | Nuked-OPN2を使用中。本チップはその移植で全声一致 | なし |
| SN76489 | | MAMEの`sn76496`を予定 | なし |
| SNES S-DSP | 外部DACへ直列デジタル出力を送り、その取得例が存在 | snes_spc（blargg）を使用中。本チップはその移植でストリーム一致 | なし |
| SID 6581、8580 | DAC以降はアナログ。参照はその前の各声2デジタル値を読む | reSID-fp（libsidplayfp）を使用中。文献実装の本チップと全声の両値で一致 | 6510上でVICEの`testprogs/SID`を予定 |

ダイから作られた、または取得値と照合された参照コアでは、その検証範囲における参照一致が実機一致の根拠になります。ロードマップがこれらを新規実装せず借りるのは、検証も付いてくるからです。

<a id="test-vectors"></a>
## テストベクトル

説得力が高いものから安いものまで4種類あり、各シートにすべて報告します。

**1. 実音楽のコーパス。** 実ゲームから取得した、チップサイクルの時刻付きレジスターログです。VGMがまさにこれで、Mega Drive、Master System、Game Boy、PC Engine向けに多数あり、1.61からNES APU書込も扱います。NESでは参照プレイヤーの書込ロガーでNSFを再生すると、Mega Man 2をテストベクトルにできます。スイープ、減衰、両ノイズモード、DMC、実際に満了する長さカウンターを覆うよう選びます。CIは約20の短いログ、全体はリリース時と必要時に実行します。

**2. テストROM。** CPUが必要です。ハーネスには各数百行の6502とSM83があり、この目的だけに使い、出荷しません。新しいROMは`$6000`／`$A000`のメモリー、古いものは画面、ビープだけのものは音から判定できる程度の本体を付けます。`pnpm --filter chipvoice-conform roms`は`packages/conform/roms`の全NES ROM、`roms:dmg`は全Game Boy ROMを実行し、`roms:sheet`と`roms:dmg:sheet`が名前別の判定をシートへ書きます。

**3. 数式テスト。** 2A03の`test/clock.mjs`は各声の速度、LFSR列長、フレームカウンター位相をデータシートと比較します。各チップに用意し、数ミリ秒で実行でき、ノイズのバグも捕らえられたはずです。

**4. ゴールデンハッシュ。** `test/golden.mjs`が固定曲をレンダーしてハッシュ化します。ドライバー、シーケンサー、コア、リサンプリング、アナログ段の全経路を固定し、どこかが動いたことを知らせます。実機へ近づいたか遠ざかったかは分からず、それは最初の3つが判断します。

<a id="the-board"></a>
## 状態表

ルートREADMEの機種別の行は、`pnpm --filter chipvoice-conform status`が`packages/conform/corpus/<chip>`のJSON、すなわち一致基準、ROM判定、ミキサー測定から書きます。数値を変える各スクリプトが状態表も再生成し、READMEの数字を人の記憶でなくハーネスの値にします。セルは印と数値で、ドライバーが届く部分や残作業の文章は`status.mjs`内で手管理し、未着手機種にもロードマップの予定行を置きます。

**完了**は4割合の平均です。参照とステップ時刻で整列するエッジ区間、ROM合格率、実機測定済みのアナログ部分（ミキサーだけなら半分）、ドライバーが使う声。弱い参照なら最初の数字は高く出るので、意図的な概数です。契約は数字でなくシートです。

<a id="the-harness"></a>
## ハーネス

`packages/conform`の`conform`。各チップに共通のコマンドを使います。

```
pnpm --filter chipvoice-conform conform 2a03 --corpus corpus/2a03 --oracle nes-snd-emu
pnpm --filter chipvoice-conform baseline     # 基準とシートの数値を再生成
pnpm --filter chipvoice-conform corpus       # 曲とスクリプトからログを再生成
node packages/conform/src/corpus/import-vgm.mjs some.vgm --out packages/conform/corpus/2a03
```

実ゲーム抽出やトラッカー出力など、NES VGMは`import-vgm`でコーパスにできます。商用ゲームの抽出物は開発者の機械に置き、保持可能なものだけを置くこのリポジトリへは入れません。

- 各ログをchipvoiceコアと参照へ通し、全サイクルの**デジタル**出力を比較します。
- ファイルごとに一致／全サイクル、最初の不一致サイクル、その前の書込、前後16サイクルの両出力を報告します。デバッガーなしでバグを探せる報告が目的です。
- 声ごとに一致数、完全／1サイクル以内／不一致のエッジ、最多エッジを揃える固定シフト、区間固有のシフトで揃う連続エッジ数を報告し、位相規約とバグを区別します。`--dump <voice>`で最初の差の周囲を並べます。
- 差があれば非0終了します。ただし`--baseline`付きなら、声の一致数がコミット済み基準より下がった場合だけ失敗します。CIはこれを使います。不完全な参照は設計上どこかで異なるので、防ぐべきは回帰です。
- 一致マーカーの間へシートの数字を書きます。人は入力しません。

参照は同梱ソースのネイティブビルドです。サンプル合成を記録先へ置き換え、初回にシステムC++コンパイラーで作ります。WebAssemblyでもよいですが、ネイティブなら1日短く済みました。

<a id="what-a-core-must-provide-to-be-testable"></a>
## 検証可能なコアに必要なもの

- **バイトの入口。** CPUと同じアドレスとバイトを受け、自分で解読します。全ログと参照が使う形式で、ドライバーに実機で不可能な操作を許さない唯一の境界です。
- **チップサイクル時刻のイベント。** `ChipSpec.clockHz`が時計を示し、サンプル内の位置にかかわらず指定サイクルへ適用します。サンプル時計をサイクル時計から導き、逆にはしません。どのサンプルレートでも同じ列は同じサイクルで書きます。
- **デジタル出力。** リサンプリングとアナログ段の前、1サイクル1値で、一致を測ります。
- **名前付きプロファイルを持つ独立したアナログモデル。** 「NES-101」「AV Famicom」をコードでなくパラメーターにします。
- **文書化した電源投入状態**と、そこへ戻る`reset()`。
- **ホストのグローバル、乱数、時刻を使わないこと。** 時計を読むコアは比較できません。

<a id="the-analog-stage-protocol"></a>
## アナログ段の手順

1. 個体を選び、モデル、改訂、年、出力経路をシートへ記載します。
2. 同じ個体を持つ人が再現できるよう、レジスター書込の試験スクリプトをコーパスへ公開します。
3. 実行中のライン出力を96 kHz、24ビットで取得します。
4. 同じスクリプトを同じプロファイルで実行し、3分の1オクターブ帯域ごとのスペクトル誤差と、各フィルターの推定コーナー周波数を比較します。
5. 最大帯域誤差、コーナー、許容差をシートへ記載します。1次段の目標は40 Hz〜15 kHzで1 dB以内です。

DACの混合曲線は手元に実機がなくても測れます。blarggの`apu_mixer`は各声をDMCのDACと打ち消し、本人の実NES録音があります。ハーネスが実行して全コアへ書込を通し、中間部の静けさを実録音と比較します（`pnpm --filter chipvoice-conform mixer`）。それがシートのミキサー行です。

リサンプリングもこの段に属します。サンプル内のサイクルを箱型フィルターで平均する方法と、帯域制限ステップ合成ではエイリアシングが違い、連続出力の「実機」そのものではありません。一致はその前で測り、影響はここで報告します。

<a id="the-sheet"></a>
## シート

[chips/TEMPLATE.md](chips/TEMPLATE_ja.md)から`docs/chips/<id>.md`に各チップ1枚を作ります。数値はハーネス、文章は手で書き、次を含めます。

- **状態**：未検証、進行中、検証済み。
- **デジタル一致**：参照、コーパス規模、一致／全サイクル、差のあるファイル、最初の差。
- **テストROM**：各名前と判定。
- **アナログ段**：個体、許容差、最大誤差、測定コーナー。
- **ドライバーの網羅範囲**：出荷ドライバーが実際に使う機能。完璧なチップでも3レジスターしか使わなければ、証明したのは3つだけです。
- **既知の差**：内容、意図的か、理由、影響。
- **出典**：実装に使った文献。

次をすべて満たすと**完了**です。

1. 全コーパスでデジタル一致100%。
2. シートの全ROMが合格。
3. 名前付き個体へのアナログ誤差が許容内。
4. 差の一覧は理由付きの意図的な項目だけ。
5. ゴールデンハッシュを記録し、CIで数式テストが合格。

シートの「検証済み」は、この一覧そのものを意味します。

<a id="rules"></a>
## 規則

- **全チップで、1ハーネス、1シート、1つの完了定義。**
- **シートなしで出荷しません。** 全行「未検証」でも構いません。空のシートは正直ですが、不在は根拠のない主張になります。
- **デジタルが先、アナログが後。** 音の個性と100%を定義できる場所はデジタルです。
- **コーパスは実音楽。** 合成試験は思いついた範囲を、実ゲームは残りを捕らえます。
- **ハッシュ変化を回帰の信号にします。** 各pushのCIでゴールデン、各リリースでコーパスのハッシュを検査します。
- **ドライバーをチップとは別に検証**し、使う範囲をシートに記載します。
- **シートへのリンクなしでREADMEに「正確」と書きません。**

<a id="composition-listening"></a>
## 作曲の試聴

実デモ、役割分離、音量を揃えた改訂比較、SNES内部のヘッドルームには[音声評価手順](AUDIO-EVALUATION_ja.md)を使います。デジタル一致と音楽の似方は別の判定です。
