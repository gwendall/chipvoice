# gamesounds のプロシージャル効果音エンジン

<p align="center">
  <a href="GAMESOUNDS-ENGINE.md">English</a> &bull;
  <a href="GAMESOUNDS-ENGINE_ja.md">日本語</a>
</p>

`packages/sfx-engine` は gamesounds.ai 独自の決定論的でオフラインの効果音
シンセサイザーです。ランタイム依存はゼロで、プレーンな TypeScript を ESM
(`dist`)にビルドして配布し、`apps/sounds`・`packages/gamesounds`・
`packages/chipvoice` には一切触れません - [Decision 52](DECISIONS.md) を
参照してください。ここでの「音」とはレシピ(JSON: どのモデルか、そのパラ
メータ、シード、サンプルレート)とそのシードの組み合わせであり、同じレシ
ピはどこでレンダリングしてもビット単位で同一の PCM になります。

<a id="architecture"></a>
## アーキテクチャ

<a id="package-layout"></a>
### パッケージの構成

| パス | 内容 |
| --- | --- |
| `src/dsp/` | オシレーター、ノイズ、エンベロープ、フィルタ、ウェーブシェイピング、ディレイ、リバーブ、ミキシングといった基本要素、そして `math.ts`(エンジン独自の決定論的な超越関数) |
| `src/models/` | 物理モデルに基づく生成器: モーダル合成、PhISEM、Karplus-Strong、バブルモデル |

| `src/rng/` | `prng.ts`、エンジン内のあらゆる乱数選択が引くシード付き PRNG(mulberry32) |
| `src/loudness/` | K 特性、モーメンタリー/インテグレーテッドの BS.1770 ラウドネス、トゥルーピーク、そしてハウスのラウドネス正規化ステップ |
| `src/presets/` | 8 個の高レベルモデル(`ui.ts`、`impact.ts`、`footstep.ts`、`whoosh.ts`、`explosion.ts`、`scifi.ts`、`magic.ts`、`pickup.ts`)と `index.ts` の `MODELS`/`PRESETS` レジストリ |
| `src/recipe/` | `Recipe` の TypeScript 型と、スキーマに基づく検証器 `assertValidRecipe` |
| `src/render/` | `renderRecipe`(最上位のエントリーポイント)、`finalize.ts`(DC 除去、ゼロへのフェード)、`bestOfN.ts` |
| `src/analysis/` | `signal-checks.ts`: レンダリングされたすべての音が満たすべき健全性チェック |
| `schema/recipe-1.json` | バージョン管理された、言語非依存のレシピスキーマ(JSON Schema draft 2020-12) |
| `parity/`、`scripts/`、`eval/` | ローカル限定の品質ツール群: クロスエンジンの決定論性、ffmpeg とのラウドネス突き合わせ、リスニングレポート、CLAP によるセマンティック評価 - 詳しくは後述の「品質の根拠」を参照 |

<a id="render-pipeline"></a>
### レンダリングパイプライン

`renderRecipe(recipe)` は次の順で実行されます。

1. **検証**: レシピを `schema/recipe-1.json` の規則に照らしてチェックしま
   す(`assertValidRecipe`)。
2. **コンパイル**: `model: "graph"` の場合は `params` をそのまま
   `GraphRecipeParams` として使います。それ以外の `model` は `MODELS`
   レジストリで引き、そのモデル自身の `compile(params, seed, sampleRate)`
   を呼びます。これも `GraphRecipeParams` を返します。高レベルモデルが音
   声そのものをレンダリングすることはなく、`renderGraph` が実行するための
   グラフを組み立てるだけです。
3. **グラフのレンダリング**(`graph/compile.ts` の `renderGraph`): ノード
   をトポロジカルソートし、すべての `{ref}`(制御レートのパッチ - エンベ
   ロープをオシレーターの周波数へ、スイープをフィルタのカットオフへ、と
   いったもの)を参照先ノードの出力に解決し、各ノードを順にレンダリング
   します。グラフ自体は最後までモノラルのままです。
4. **仕上げ**(`render/finalize.ts`): DC オフセットを差し引き、最後の 6ms
   を線形にフェードして正確にゼロにします。これにより、そのエンベロープ
   がどう終わろうと、すべてのレンダリングは真のゼロクロッシングで終わり
   ます。
5. **ラウドネスの正規化**(`loudness/normalize.ts`)をハウスの規約に合わ
   せて行います(「ラウドネスとミキシング」を参照)。
6. **ステレオへのパン**を最後に一度だけ行います(`dsp/mix.ts` の等パワー
   な `panToStereo`) - 上記の DSP プリミティブはすべてモノラルのままで、
   それぞれをシンプルに保ち、レシピのノード数も小さく保てます。

<a id="determinism"></a>
## 決定論性

<a id="why-this-matters"></a>
### なぜ重要か

ブリーフの必須要件です: 同じレシピとシードは Node・Chromium・Firefox・
WebKit のどこでもビット単位で同一の PCM をレンダリングしなければなりませ
ん。これにより、レシピはエンジンによってずれることのない、ある音の正確で
可搬な記述になります。

<a id="how-it-is-enforced"></a>
### どう強制しているか

ECMA-262 は `+`、`-`、`*`、`/`、そして `Math.sqrt`・`Math.round`・
`Math.floor`・`Math.abs` などについては正確な IEEE-754 倍精度の結果を義務
付けていますが、超越関数(`sin`、`cos`、`exp`、`log`、`pow`、`tanh` など)
については明示的に「実装依存の近似」としています。V8・SpiderMonkey・
JavaScriptCore はそれぞれ異なる libm を積んでおり、最後の 1〜2 ビットで食
い違わない保証はどこにもありません。`dsp/math.ts` は、エンジンが必要とす
るすべての超越関数を `+`、`-`、`*`、`/` だけから実装しています(標準的な
fdlibm のレンジリダクションの形 - 引数を、テイラー/マクローリン級数が倍精
度をはるかに超えて収束する小さな区間に還元し、それから再構成する。出典は
そのファイル自身のドキュメントコメントを参照)。そのため DSP のコアは
`src/` のどこでも `Math.sin`・`Math.cos`・`Math.exp`・`Math.log`・
`Math.pow`・`Math.tanh` を直接呼びません。唯一の例外は `Math.sqrt` で、そ
のまま使っています: IEEE-754(したがって ECMA-262)はこれを正しく丸める
ことを要求しており、どのエンジンもそれを守っているためです。シード付き
PRNG(`rng/prng.ts`、mulberry32)も超越関数には触れません - 32 ビット整数
乗算(`Math.imul`、仕様どおり正確)とビット演算(これも仕様どおり正確)だ
けを使います。

<a id="cross-engine-parity-harness"></a>
### クロスエンジンのパリティハーネス

`parity/`(chipvoice 自身の `scores/render-parity/` をモデルにした、ローカ
ル限定で CI には含まれないツール - chipvoice の render-parity と同じパタ
ーン)は 82 個の入力をレンダリングします - 53 個の名前付きプリセットをそ
れぞれの基準シードで、各ファミリーの代表プリセット 1 つをさらに 3 つのシ
ードで、そして名前付きプリセットだけでは到達しないノード種別やフィルタ/
シェイパーの種類(`karplus`、フィルタの `comb` と `allpass-delay`、シェイ
パーの `srr`、そして `exp()` を直接使うダンプドディレイの
`loopFilterCutoff`)を狙って手書きした低レベルのグラフレシピ 5 個です。
これらを Node で、それから Playwright 経由で実際の Chromium・Firefox・
WebKit でレンダリングし、PCM を SHA-256 で比較します。`parity/self-test.mjs`
は、ある 1 入力の PCM の 1 サンプルをハッシュ化前にわざと壊し、その行だ
けが不一致になることを確かめることで、比較そのものが実際に機能すること
を証明します。

`pnpm --filter sfx-engine parity:check` でローカル実行できます。82 個の
入力すべてが Node・Chromium・Firefox・WebKit の間でビット単位で一致しま
した。`dsp/math.ts` が設計上すでに置き換えている以上に置き換えが必要な
`Math.*` 関数は見つからず、乖離するものはありませんでした。

<a id="recipe-format"></a>
## レシピの形式

`schema/recipe-1.json`(JSON Schema、draft 2020-12)がバージョン管理され
た正となる仕様です。

```json
{
  "engine": "sfx-engine@1",
  "model": "impact",
  "params": { "material": "metal", "weight": "heavy" },
  "seed": 7,
  "sampleRate": 48000
}
```

<a id="two-layers"></a>
### 2 つの層

- **低レベルのグラフ**(`model: "graph"`): `params` は `GraphRecipeParams`
  です - `duration`、`nodes` の配列(`id`、`type`、`params`、任意の
  `inputs`)、出力ノードの `output`、そして任意の `pan`。ノードの `type`
  は `const`、`oscillator`、`noise`、`envelope`、`sweep`、`filter`、
  `shaper`、`delay`、`reverb`、`mix`、`multiply`、`modal`、`phisem`、
  `karplus`、`bubble` のいずれかです。ノードの `params` は、変調可能と文
  書化されているフィールド(オシレーターの `freq`、フィルタの `cutoff`
  など)であれば、単なる数値の代わりに `{ref: "nodeId"}` を持てます。こ
  れは他のノードのレンダリング済み出力を制御レートの変調として差し込みま
  す。
- **高レベルの名前付きモデル**(`ui`、`impact`、`footstep`、`whoosh`、
  `explosion`、`scifi`、`magic`、`pickup`): `params` はそのモデル自身の形
  (例えば `impact` の `{ material, weight?, size? }`)で、レンダリング前
  に内部で `GraphRecipeParams` にコンパイルされます。すべてのモデルは機
  械可読な `metadata`(`ModelMetadata`、`src/presets/types.ts`)を公開し
  ます: 平易な英語での説明、各パラメータの型/単位/範囲/デフォルト/平易な
  意味、どのパラメータがシードごとにどれだけ揺らぐかの注記、そしてすぐに
  レンダリングできる名前付きの例 2〜4 個です。このエンジンの上に構築され
  る API は、このメタデータをそのままエージェントに提示でき、エージェン
  トはこのパッケージのソースを一切読まずにパラメータを選べます。

<a id="example"></a>
### 例

`recipeForPreset("impact-metal-heavy", 7, 48000)` は次を返します。

```json
{
  "engine": "sfx-engine@1",
  "model": "impact",
  "params": { "material": "metal", "weight": "heavy" },
  "seed": 7,
  "sampleRate": 48000
}
```

これは(`impact` 自身の `compile` によって)単一の `modal` ノード - 打撃
を受けた金属オブジェクトの減衰する共振モードの集合 - にコンパイルされ、
`size` は「heavy」のデフォルト値を中心にシードから ±6% 揺らぎます。

<a id="models-and-presets"></a>
## モデルとプリセット

<a id="the-eight-high-level-models"></a>
### 8 個の高レベルモデル

| モデル | ファミリー | 構成要素 |
| --- | --- | --- |
| `ui` | ui | 短い ADSR エンベロープで整形されたオシレーター |
| `impact` | impact | モーダル合成(材質ごとの減衰する共振モード) |
| `footstep` | footstep | 表面ごとにチューニングされた PhISEM の粒子衝突 |
| `whoosh` | whoosh | フィルタリングしてスイープさせたノイズ |
| `explosion` | explosion | 重ねたフィルタ済みノイズ、サブベースのオシレーター、PhISEM の瓦礫 |
| `scifi` | scifi | スイープするオシレーター、FM/リングモジュレーション、フィルタ |
| `magic` | magic | 重ねたオシレーター、ディレイ、アルゴリズミックリバーブ |
| `pickup` | pickup | 重ねた短いトーン系のブリップ、ADSR で整形 |

<a id="continuous-params"></a>
### 連続パラメータ

`impact`、`ui`、`whoosh` は最初から連続パラメータ(`size`、`baseFreq`、
`intensity`)を持っていました。`scifi`、`magic`、`pickup`、`footstep`、
`explosion` はもともと enum/真偽値(`kind`、`weight`、`debris`)しか公開
していませんでしたが、この 5 モデルもそれぞれ 2〜4 個の連続パラメータを
持つようになりました。いずれも実際のコンパイル時のつまみに結び付いてお
り(見せかけのラベルではありません):

| モデル | 新しいパラメータ | 何をスケールするか |
| --- | --- | --- |
| `scifi` | `pitch`(半音、-12〜12)、`duration`(倍率、0.4〜2.5)、`brightness`(0〜1) | すべてのベース周波数/スイープの両端。各分岐のベース時間。キューの最後段のローパス(1 未満のとき) |
| `magic` | `pitch`、`duration`、`brightness`(範囲は `scifi` と同じ) | すべてのジェスチャートーンとスパークルの中心周波数。各 kind のベース時間。キューの最後段のローパス |
| `pickup` | `pitch`、`duration`、`brightness`(範囲は同じ) | すべてのベース周波数(`key` は直接の周波数つまみを持たないため、`models/modal.ts` の `size` を介して逆方向にスケール)。各 kind のベース時間。キューの最後段のローパス |
| `footstep` | `intensity`(0〜1、`weight` の連続版)、`pitch`(半音、-12〜12) | それまで `weight` で切り替えていたすべての量(サイズ/強さ/エネルギー/時間)。concrete/wood/metal のみのモーダル `size` - gravel/snow/grass/water-puddle では無効であることを明記(`models/phisem.ts` に周波数上書きの入力がなく、grass/water-puddle は音高のないノイズであるため) |
| `explosion` | `distance`(0〜1、"distant" の連続版)、`debrisAmount`(0〜1、`debris` の連続版)、`duration`(倍率、0.4〜2.5) | リバーブのサイズ/ダンピング/ミックス、リバーブ後のマフルのカットオフ、時間ボーナスをまとめてスケール。瓦礫レイヤーの粒子数とミックスゲインをまとめてスケール。ブーム/サブベース/瓦礫のベース時間 |

新しいパラメータはどれも、デフォルト値ではモデルの既存の名前付きプリセ
ットのレンダリングをビット単位で完全に再現します: `presets/helpers.ts`
の `lerpExact(lo, hi, t)` は `t<=0`/`t>=1` のとき `lo + (hi-lo)*t` を計算
せず(IEEE754 ではこの式が境界で厳密に一致する保証がないため)`lo`/`hi`
をそのまま返し(浮動小数点演算を一切行いません)、`semitoneMultiplier(0)`
も厳密に `1` になります(`0/12` と `2**0` はどちらも IEEE754 で厳密な値
です)。`pnpm --filter sfx-engine test:hash-fixture` はこれを直接確認して
います: 159 個すべてのハッシュ(53 プリセット x 3 シード)がこの作業によ
って変化していません。

8 モデルすべての `compile()` が(直接、または `sparkleLayer` を介して間
接的に)呼び出す `seededRange` のジッターはすべて `ModelMetadata.seedJitter`
に `{ label, affects, min, max }` として宣言されています - `label` は
`seededRange` のプレフィックス、`affects` はそれが変化させる量のプレー
ンイングリッシュでの説明、`min`/`max` は `seededRange` に実際に渡される
乗算オフセットそのもの(例: +-10% なら `-0.1`/`0.1`)です。これは
`test/seed-jitter-coverage.test.mjs` によって機械的に検証されています。
このテストはすべてのプリセットと各モデルのメタデータの `examples` をコ
ンパイルし、`seededRange` を計装して、捕捉した `(label, min, max)` が、
プレフィックスが一致し境界値も厳密に一致する宣言済みエントリでカバーさ
れていない場合(または宣言済みエントリが一度も使われていない場合)に失
敗します。1 つ例外があります: `sparkleLayer` の粒の発音タイミングのジッ
ター(`label` が `-t` で終わるエントリ)は、生の秒数ではなくキュー自身
の時間に対する割合として宣言されています - 固定の秒数では、測定した時
だけ以外のどの時間でも誤った値になってしまうためです。テストはこのエン
トリの宣言された境界値を、各レンダリングの実際にコンパイルされた
`duration` でスケールしてから比較します。宣言済みのエントリはモデルご
とに次のとおりです:

| モデル | ラベル | 影響する量 | 範囲 |
| --- | --- | --- | --- |
| `scifi` | `laser-pitch` | レーザースイープの開始周波数 | +-10% |

<a id="loudness-and-mixing"></a>
## ラウドネスとミキシング

<a id="house-convention"></a>
### ハウスの規約

`loudness/loudness.ts` と `loudness/truepeak.ts` は ITU-R BS.1770-4 /
EBU R128 を実装しています: K 特性(2 段のカスケードされたビクアッド、
44100Hz と 48000Hz の両方で BS.1770 の設計パラメータから導出し、48kHz で
は ITU 自身が公開している係数と 1e-9 の精度で一致することを確認済み)、
モーメンタリーラウドネス(400ms ブロック。400ms より短いレンダリングでは
信号全体を 1 ブロックとして扱うフォールバック)、インテグレーテッド(ゲー
ト処理された)ラウドネス、そしてトゥルーピーク(ウィンドウ付き sinc 補間
による 4 倍オーバーサンプリング)。`loudness/normalize.ts` はその後、す
べてのレンダリングにゲインをかけ、モーメンタリーラウドネスが最大でも
-18 LUFS、トゥルーピークが最大でも -1 dBTP になるようにします。両者が食
い違う場合はピークの上限が優先されます。

<a id="ebu-tech-3341-minimum-requirements-tests"></a>
### EBU Tech 3341 の最小要件テスト

`test/loudness.test.mjs` は EBU Tech 3341 v4(2023 年 11 月、ジュネーブ)
の Table 1 にある最小要件テストのケース 1〜5 と 15〜19 を実装しており、
ケース番号と期待値はその表から直接引用しています:

- **ケース 1〜2**(ラウドネス): -23.0dBFS と -33.0dBFS の定常 1kHz トー
  ン。モーメンタリーラウドネスとインテグレーテッドラウドネスを表の期待
  値に固定しています。
- **ケース 3〜5**(ラウドネス): 2 段階のゲート(絶対 + 相対)を働かせるよ
  うに作られた信号。インテグレーテッドラウドネスを固定しています。
- **ケース 15〜19**(トゥルーピーク): fs/4、fs/6、fs/8 でのさまざまなサ
  ンプル間位相を持つ 0.5/1.41 フルスケールのトーンを、表のケース 15 の
  本文が指定する 10ms のフェードイン/フェードアウトで整えたもの(整えて
  いない、急に途切れる信号では、実際のフィルタ精度とは無関係なトゥルー
  ピーク補間器の端の擬似的なアーティファクトが出ることが開発中に判明し
  ました - これは本番のテストにコミットする前にプローブで検出して修正
  済みです)。トゥルーピークは表の +0.2/-0.4dB の許容値で固定しています。
- ケース 6(マルチチャンネル)、7〜8(実際の番組素材)、9〜14(ショートタ
  ーム専用で、このモジュールは S 測定値を公開していません)、20〜23(こ
  のエンジンの近似的なトゥルーピークフィルタが主張する精度を超える、よ
  り厳しいトランジェント再構成テスト)は対象外とし、テストファイルにそ
  の旨を明記しています。

Table 1 のケースはステレオですが、このエンジンはモノラルです。そのため
各期待値は、表のステレオでの数値から正確に `-10*log10(2) = -3.0103` LU
だけシフトしています。これは BS.1770 の重み 1.0 で完全に同一な 2 チャン
ネルが 1 チャンネル分に対して寄与する厳密なラウドネス量です(規格自体の
式の合算から導かれる厳密な値であり、経験的な調整ではありません - トゥル
ーピークは BS.1770 の附属書 2 がチャンネルの合計ではなく最大値を取るた
め、シフトは不要です)。以前の非標準な「約 -3.0 LUFS ±0.3」というフルス
ケールのスモークテストは、同じくケース 1 由来のシフトを使い、丸めた俗説
的な値ではなく `-3.0103 ±0.1` LU として解析的に固定した値に置き換えまし
た。2 つの陰性テスト(K 特性をバイパスした場合と、相対ゲートを外した場合
をそれぞれ再実装したもの。どちらもテストファイル内だけの実装で、実際の
パッケージからはエクスポートされません)により、K 特性と相対ゲートの各段
が実際に効いていることを示しています: K 特性をバイパスするとケース 1 の
値が 0.691LU ずれ、相対ゲートを外すとケース 3 の値が 1.155LU ずれ、いず
れも許容値 0.1LU を大きく超えます。

<a id="cross-check-against-ffmpeg"></a>
### ffmpeg との突き合わせ

`scripts/ffmpeg-loudness-check.mjs` はすべてのプリセットをレンダリングし、
このエンジン自身の `integratedLoudness()`/`truePeakDb()` を、同一信号の
モノラル WAV に対する ffmpeg の `ebur128` フィルタ - 同じ規格の独立した実
装 - と比較します。トゥルーピークは 53 プリセットすべてで比較しています
(瞬間的な統計量であり、どんな長さでも意味があるため): 観測された最大差
は 0.100dB、許容値は 0.25dB(およそ 2.5 倍の余裕)。インテグレーテッドラ
ウドネスは 0.4 秒以上ある 28 個のプリセットでのみ比較しています: ffmpeg
の `ebur128` フィルタは BS.1770 のゲーティングブロック(400ms)1 個分に満
たないクリップでは有効なインテグレーテッド値を出せず、内容にかかわらず
絶対ゲートの下限値(-70.0 LUFS)を返します。この境界を正確に確認しました
(0.400 秒のプリセットは ffmpeg とすでに差 0.000 LU で一致し、それより短
いプリセットはすべて内容にかかわらず ffmpeg から正確に -70.000 LUFS が返
りました)。比較可能な 28 プリセットのうち、観測された最大差は 0.058 LU、
許容値は 0.25 LU(およそ 4 倍の余裕)です。両方の許容値とも、測定された分
布に明記したマージンを足して導いたものであり、今日の出力を通すために選ん
だものではありません。

<a id="loudness-convention-across-engines"></a>
### エンジン間でのラウドネス規約

このエンジン自身の `loudness/normalize.ts` は、ここで作られるすべてのレ
シピが 1 チャンネルでレンダリングされるため、モノラルとして測定しゲイン
をかけています。gamesounds.ai のカタログビルド
(`apps/sounds/scripts/lib/audio.mjs` の `levelToConvention`。上限は同じ
-18 LUFS モーメンタリー / -1 dBTP トゥルーピークで、優先順位も同じくピー
クが勝ちます)は、代わりに各ファイルをその実際に出荷されるチャンネルレ
イアウトのまま測定し、レベル調整します - カタログのソースの大半はステレ
オ 44.1kHz です。BS.1770 のチャンネル合算により、モノラル信号は、同一の
内容を(デュアルモノの)2 チャンネルとして再生した場合より約
`-10*log10(2) = -3.0103` LU 低く読み取られます。これは、上の Table 1 の
ステレオのテストケースがまさにその分だけシフトを必要とした理由と同じで
す。つまり、このエンジンでちょうど -18 LUFS になるようゲインをかけたレ
ンダリングは、再生すると、名目上 -18 LUFS のカタログの音より、聴感上お
よそ 3dB 大きく聞こえます。カタログのメーターがこのエンジンのメーターに
は見えない 2 つ目のチャンネルを加味しているためです。これは丸め誤差では
なく実在するエンジン間の不整合であり、本 PR ではこれを直すためにどちら
のエンジンの正規化も変更していません。sfx-engine をカタログに組み込む
GS-03 で、これを解消する必要があります: sfx-engine のすべてのレンダリン
グを、その実際に出荷されるチャンネルレイアウト(モノラルのまま、または
先にステレオに複製する。手続き的な音についてカタログが最終的に何を出荷
するか次第)でカタログ自身の `levelToConvention` に通して再レベル調整す
るか、あるいはカタログ全体でモノラルとして出荷・測定を一貫させるか、い
ずれかです。どちらの方法でも、両エンジンの音が紙の上の数値だけでなく、
聴き手の耳の中でも同じ -18 LUFS になるようにする必要があります。

<a id="clap-semantic-eval"></a>
### CLAP によるセマンティック評価

客観的で、CI には含まれないローカル限定のチェックです: 汎用のテキスト・
音声モデルは、これらの音を実際にその 1 行の説明と一致するものとして認識
するでしょうか?
[LAION-CLAP](https://github.com/LAION-AI/CLAP)(PyPI の `laion_clap`、
`630k-audioset-best.pt` の非フュージョンチェックポイント - コードもチェ
ックポイントも CC0-1.0 であることを、リポジトリ自身の `LICENSE`、
`pip show laion_clap` の `License` フィールド、そしてチェックポイントの
ホスト先である https://huggingface.co/lukewys/laion_clap から確認済みで
す。したがってローカルでの利用に制限はありません)を、`.artifacts/`
(gitignore 対象)の下の Python venv で使っています。評価スクリプト自体
は `eval/clap_eval.py` として追跡管理されており、依存パッケージのバージ
ョンは `eval/requirements.txt` に固定されています:

```
python3 -m venv packages/sfx-engine/.artifacts/venv
packages/sfx-engine/.artifacts/venv/bin/pip install \
  numpy==1.26.4 scipy==1.17.1 torch==2.14.0 laion_clap==1.1.7

# packages/sfx-engine/ から
node scripts/build-clap-audio.mjs
.artifacts/venv/bin/python3 eval/clap_eval.py
```

`eval/prompts.json` はプリセット 1 つにつき 1 つ、平易な英語での音の説明
53 個からなる固定セットで、これを実行する前に一度だけ書き、その後は編集
していません - プリセットはこれらのプロンプトに対してチューニングされて
いないため、ホールドアウト用の 2 つ目のプロンプトセットはありません(こ
の評価に対して何かを反復チューニングしたことはないため)。
`scripts/build-clap-audio.mjs` は 48kHz モノラルの WAV セットを、4 個の
シード(`SEEDS = [1, 2, 3, 4]`。各プリセット固有の参照シードだけではあ
りません)それぞれについて 2 つレンダリングします: `real`(すべてのプリ
セットを通常どおり)と `degraded`(同じプリセット/シードのコンパイル済
みグラフを `scripts/clap-degrade-graph.mjs` に通したもの。これはすべての
`filter`/`shaper`/`delay`/`reverb` ノードを取り除き、すべての
`envelope`/`sweep` ノードを定数に平坦化し、物理モデルに基づく生成器 -
`modal`、`phisem`、`karplus`、`bubble` - をすべて単純なホワイトノイズに
置き換えます。配線自体はそのままで、生のオシレーター/ノイズ/定数だけが
残ります)。`eval/clap_eval.py` は 53 個のプロンプトと両方の音声セットを
すべて埋め込み、シードごとに独立した 53 プロンプト対 53 音声の検索を行
い(あるアイテムの正解は常にその同じシードの 53 個の候補の中にあり、シ
ード間で混ざることはありません)、その結果得られるアイテム・シードごと
のヒット/ミスを、以下の記述的な比率のために条件ごと 212 試行にプールし
ます。ただし、1 つのプリセットの 4 回のシードレンダリングは独立した試
行ではありません - シードはレシピを数パーセントしか揺らさないためです
(上記「連続パラメータ」の `ModelMetadata.seedJitter` を参照)。したが
って以下のすべての有意性検定は、(アイテム、シード)の試行(n=212)で
はなく、プリセット(n=53)を分析の単位として扱います。

| 条件 | 何を測るか |
| --- | --- |
| `real` | このチケットが CLAP の結果として報告する数値 |
| `shuffled labels` | 同じ音声とプロンプトを、シャッフルした(擾乱)対応関係で採点したもの。シードごとに 5 回、合計 20 回のランダムな擾乱で平均を取っています - 検索手法そのものの健全性チェックであり、チャンスレベルになることを期待しています |
| `degraded engine` | 同じプロンプトを degraded 音声セットに対して採点したもの - `real` より明確に悪いスコアにならなければ、この指標は何も測っていないことになります |

**数値(`.artifacts/clap-report.json` より、laion_clap
`630k-audioset-best.pt`、非フュージョン、4 個のシードをプールした条件ご
と 212 試行)**

| 条件 | top-1 | top-5 |
| --- | --- | --- |
| `real` | 10.4%(22/212) | 37.7%(80/212) |
| `shuffled labels` | 1.4%(理論上のチャンスレベル 1.9%) | 8.9%(理論上のチャンスレベル 9.4%) |
| `degraded engine` | 4.7%(10/212) | 21.7%(46/212) |

**事前に宣言した統計検定(有意水準 0.05、厳密検定)**: 分析の単位は(ア
イテム、シード)の試行(n=212)ではなく、プリセット(n=53)です - 1 つ
のプリセットの 4 回のシードレンダリングはレシピを数パーセント揺らすだ
けの違いしかないため、独立したベルヌーイ試行ではなく相関しており、これ
を 212 個の独立した試行として扱うと(この評価の以前のバージョンはまさ
にそうしていました)、以下のすべての p 値が過小評価されます。`real` と
`degraded` のチャンスに対する検定には、厳密な置換(ランダム化)検定を
使っています: 反復回数 `NUM_PERMUTATION_REPS = 10000`、乱数シード
`PERMUTATION_RNG_SEED = 20260929`(どちらも `eval/clap_eval.py` 内)。各
反復では、プロンプトと音声の対応関係の置換を 1 つだけ引き、その同じ置換
を 4 個のシードすべてに適用してから、それらの top-k ヒット数を合計し、
そのプール済み合計の経験的な帰無分布を作ります。この置換をシードごとに
引き直すのではなくプリセットの 4 シードで共有しているのは、帰無仮説の
下で交換可能な単位が(アイテム、シード)の試行ではなくプリセットだから
です: 実データでは 1 つのプリセットの 4 回のシードレンダリングは相関し
ています(シードはレシピを数パーセントしか揺らしません)。そのため帰無
分布も同じように相関させなければならず、そうしなければ本来の帰無分布よ
り狭くなり、以下のすべての p 値が過大評価されます(この評価の以前の版
はシードごとに独立した置換を引いており、まさにこのバグを抱えていまし
た)。スクリプト内のセルフチェック `_self_check_permutation_clustering()`
は、この修正が効いていることを証明します: 1 つのプリセットの 4 シードが
まったく同一である合成埋め込みを使うと、共有置換による帰無分布の標準偏
差は単一シードの標準偏差のちょうど 4 倍になり(独立したシードごとの置換
なら得られるはずの約 2 倍にはなりません。これは 4 つのほぼ独立した抽出
を合計するか、1 回の抽出の複製を 4 つ合計するかの違いです)。検討したも
う一つの案(プリセットごとに「4 シード中 k 回以上ヒット」をそのしきい値
イベントの正確なチャンスレートに対して二項検定する方法)ではなく置換検
定を選んだのは、想定上の試行あたりチャンスレートではなく実際の埋め込み
空間の幾何構造を直接使えること、プリセット
のシード間の独立性を一切仮定する必要がないこと、そして「4 回中 k 回以
上」に二値化することで失われる 0〜4 のヒット数の大きさの情報を捨てずに
済むことによります。`real` 対 `degraded` の検定には、53 個のプリセット
それぞれの(hits_real - hits_degraded、4 シード中)についての対応のある
厳密符号検定を、同数(タイ)を除外し、片側で実施しています。`shuffled`
はこれらのプリセット単位の検定には含まれません: 検索手法そのものが正
解の対応に対して偏っていないかを確認する、プールした両側の健全性チェッ
クのままであり(この評価が根拠として依拠する主張ではありません)、した
がって(上記「数値」の表にある)記述的な比率としてのみ報告し、以下の有
意性の表には含めません。

| 検定 | top-1 の p 値 | top-5 の p 値 |
| --- | --- | --- |
| `real` 対チャンス(置換検定、上回る) | <0.0001(有意) | <0.0001(有意) |
| `degraded` 対チャンス(置換検定、上回る) | 0.0585(有意でない) | 0.0004(有意) |
| `real` 対 `degraded`、プリセット単位の対応のある符号検定(real が上回る) | 0.395(有意でない) | 0.055(有意でない) |

以下のプール試行の二項検定の p 値は独立した試行を仮定していますが、上
記のシードのクラスタリングによりその前提は成り立たないため、有意性検定
としては採用せず、`.artifacts/clap-report.json` の中で記述的な比率とし
てのみ保持しています。`*_pooled_212_DESCRIPTIVE_ONLY` というラベル(real
対チャンス top-1 p=1.61e-10、top-5 p=1.40e-28; degraded 対チャンス
top-1 p=0.0075、top-5 p=7.38e-08 - いずれも上記の正しいプリセット単位の
数値よりずっと極端であり、非独立性が生む過大評価のパターンそのものです)
と、`shuffled_vs_chance_pooled_DESCRIPTIVE_ONLY`(53 プリセット×4 シー
ド×5 擾乱 = 1060 試行、両側: top-1 p=0.309、top-5 p=0.563)です。このセ
クションの、プリセット単位の書き直しより前の版では、プール 212 試行の
real 対 degraded の対応のある符号検定(top-1 p=0.0251、top-5 p=0.00062、
いずれも「有意」)も報告していました。この数値は同じクラスタリングの理
由で無効として破棄しており、上記の数値と突き合わせて調整してはいませ
ん。

率直に、言い換えることなく読むと: `real` は top-1・top-5 の両方でチャン
スを明確に上回っています - このエンジンの音声は、汎用のテキスト・音声
モデルにとって実際に検索可能であり、単にノイズと表面的に違うだけではあ
りません。`degraded` も top-5 ではチャンスを上回っています(p=0.0004)
が、置換検定の帰無分布がシードのクラスタリングを正しく考慮するようにな
った結果、top-1 ではもはやチャンスを上回っていません(p=0.0585、有意水
準 0.05 をわずかに超えています): 削ぎ落としたノイズベースのレンダリン
グでも、長さ・大まかなスペクトル傾斜・オンセットのリズムといった信号は
top-5 で認識できる程度には残っていますが、単独の最良一致として確実に選
ばれるほどではない、ということです。これは、この評価の以前の一時点がこ
こで報告していた数値(top-1 p=0.0066、「有意」)からの変更です - あの数
値は置換検定そのもののバグ(1 つのプリセットの 4 シードにまたがって反復
ごとに 1 つの置換を共有するのではなく、シードごとに独立した置換を引いて
いた)によるもので、帰無分布が本来のクラスタリングされた帰無分布より狭
くなり、この行のすべての p 値が過大評価されていました。上記のセルフチ
ェックはそのバグのために存在します。プリセット単位で見ると、独立した単
位はわずか 53 個しかなく、`real` は統計的に有意な水準で `degraded` を上
回って**いません**: プリセット単位の対応のある符号検定は top-1 で
p=0.395(53 個のプリセットのうち `real` が上回ったのが 8 個、`degraded`
が上回ったのが 6 個、同数が 39 個)、top-5 で p=0.055(21 対 11、同数 21
個)となり、有意水準 0.05 に近いものの、その外側にあります。これは、こ
の同じ比較を top-1・top-5 のどちらでも有意と報告していた以前の、プリセ
ット単位の書き直しより前の(無効な、プール 212 試行の)分析からの、実質
的な後退です。正直な読み方をすれば、この評価は 53 プリセットという規模
では、フィルタ/エンベロープ/物理モデルに基づく生成器が degraded コント
ロールに対して CLAP の認識性を測定可能なほど改善していると確認できるだ
けの統計的検出力を持っていない、ということです。`real` の記述的な数値
(top-5 で 37.7% 対 `degraded` の 21.7%)はその方向を示唆してはいますが。
同じ 53 個のプリセットのレンダリングをさらにシードで増やしても、これは
解決しません - シードはまさにこの問題を引き起こしている、相関した非独
立の軸だからです。解決するとすればプリセット数を増やすことです。

ファミリーごとの混同(`real` 条件、top-1 予測、4 個のシードをプール。行
はプロンプトの実際のファミリー、列は CLAP が最も類似していると判定した
プリセットのファミリーです。各行の合計はそのファミリーのプリセット数×
4 シードになります):

| 実際 \ 予測 | ui | impact | footstep | whoosh | explosion | scifi | magic | pickup |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| ui | 8 | 13 | 6 | 0 | 0 | 7 | 0 | 2 |
| impact | 8 | 32 | 0 | 0 | 0 | 8 | 0 | 0 |
| footstep | 0 | 16 | 11 | 1 | 0 | 0 | 0 | 0 |
| whoosh | 0 | 0 | 0 | 16 | 0 | 0 | 0 | 0 |
| explosion | 0 | 5 | 0 | 0 | 1 | 2 | 4 | 0 |

この行列の対角成分は、上記の見出しの数値よりも緩い指標です: 「CLAP の
top-1 の推測が、正確なプリセットを外していたとしても、とにかく正しいフ
ァミリーに入っていたか」というものです。見出しの `real` top-1 率を実際
に裏づけているのは、より厳しい指標、すなわちファミリーごとの正確なプリ
セットの一致です:

| ファミリー | 正確な top-1 ヒット数 / 試行数 | 割合 |
| --- | --- | --- |
| ui | 0/36 | 0% |
| impact | 8/48 | 16.7% |
| footstep | 2/28 | 7.1% |

正直に読み解くと: この厳しい方の、正確なプリセットの指標では、`whoosh`
が群を抜いて強く(7/16、43.8%)、`impact`(8/48、16.7%)、`scifi`
(4/32、12.5%)がこれに続きます。`ui`・`magic`・`pickup` はいずれもちょ
うどゼロ(0/36、0/20、0/20)で、`footstep`(2/28、7.1%)と `explosion`
(1/12、8.3%)もゼロをわずかに上回るだけです。上記の混同行列によるファ
ミリー対角の緩い読み方はもっと寛容です - CLAP の top-1 の推測は、正確な
プリセットを外していても `impact` で 66.7%、`footstep` で 39.3%、
`whoosh` では 100% が正しいファミリーに入っています - しかし 3 つのファ
ミリー(`magic` の 0/20、`pickup` の 4/20、`explosion` の 1/12)はどちら
の読み方でも弱いままです。`magic` の top-1 の推測は 20 回中 13 回が
`pickup` でした。これはランダムな失敗というより、もっともらしい混同で
す(どちらも短く、明るく、トーン的なブリップで、同じ構成要素 - ADSR で
整形した短いトーンの重ね合わせ - を土台にしています)。`footstep` も
`impact` と推測される方が半分を超えています(16/28)。これも検索が壊れ
ている兆候ではなく、もっともらしいペアです(どちらも短い過渡的な衝突音
です) - それは上記の `shuffled` コントロールがすでに否定しています。

以前の、シード 1 個だけの統計検定以前の版のこの評価では、上記のファミ
リー対角の読み方について「explosion 0/3」「pickup 1/5」といった数値が非
公式に引用されていました。これらは、この評価が固定された依存バージョ
ン・追跡管理されたスクリプトのパス・事前宣言された統計検定を持つ前に行
われた、シード 1 個だけのスポットチェック(このセクションのプールした
数値より試行数がそれぞれ 12 分の 1・20 分の 1)であり、本セクションのプ
ールされ統計的に検定された結果に置き換えられたものであって、突き合わせ
て一致させるべきものではありません。

もし上記の事前宣言済みの検定が `real` がチャンスを上回ることを示してい
なかったり、`shuffled` がチャンス以外の振る舞いを示していたりした場合、
このセクションはその数値を品質の証拠として引用せず、その旨をはっきりと
書きます。実際にはそうではありませんでした。一方で、シードのクラスタリ
ングを考慮すると `real` 対 `degraded` が有意性を失うことは示されており、
さらに、置換検定の帰無分布を修正して 1 つのプリセットの 4 シードにまた
がって反復ごとに 1 つの置換を実際に共有するようにした結果、`degraded`
自体も top-1 でチャンスに対する有意性を失っています(p=0.0585。バグの
あった、過大評価する帰無分布のもとでは p=0.0066 でした) - どちらも取り
繕うことなく上記で率直に報告しています。`real` の数値は top-1・top-5 の
どちらでもチャンスを上回る根拠として成立しますが、(この試行数の規模で
は)まだ degraded コントロールを上回る根拠としては成立しません。この根
拠が示さないものの詳細は、後述の「この根拠の限界」を参照してください。

<a id="best-of-n-helper"></a>
### Best of N ヘルパー

`render/bestOfN.ts` は同じレシピを N 個の異なるシードでレンダリングし、
最も高いスコアのものを返します: `analysis/signal-checks.ts` の健全性チェ
ックは常に実行され、任意の外部 `score` 関数(例えばテキストプロンプトに
対する CLAP の類似度スコアを別プロセスで計算したもの - このパッケージに
ML のランタイム依存はありません)はデフォルトの重み 0.6 でブレンドされま
す。設計上決定論的です(同じベースレシピとシードのリストは常に同じ PCM
をレンダリングし、したがって同じスコアになります)。`test/best-of-n.test.mjs`
がこれを直接検証しています(2 回の実行が同じ勝者・スコア・PCM を生み出す
こと、シードが並べ替えられずに与えられた順に消費されること、外部スコアの
ブレンドが文書化されたデフォルトの重みを使い、明示的な重みも尊重すること、
そして否定的なケース(意図的に無音な低レベルグラフレシピが、スタブではな
く実際のシグナルチェックの経路を通じてスコア 0 になること))。

<a id="limits-of-this-evidence"></a>
### この根拠の限界

- モーダル合成のモードテーブル(`models/modal.ts`)は一般的な音響原理から
  設計されたものであり、測定した物体に合わせてフィッティングしたもので
  はありません - そのファイル内でそう明記されており、測定された事実とし
  ては主張していません。
- `truepeak.ts` のトゥルーピークフィルタは、ウィンドウ付き sinc の多相補
  間器であり、ITU Annex 2 自身が公開しているフィルタテーブルをビット単位
  で再現したものではありません。上記の ffmpeg との突き合わせは、その近似
  が実際にどれだけ近いかの根拠であり、規格適合を主張するものではありませ
  ん。
- `models/bubble.ts` は、一部の録音に見られるオンセットのチャープ(気泡が
  発生源から離れる際に周波数がわずかに滑る現象)をモデル化していません -
  既知の、文書化された単純化であり、実装されていません。
- CLAP 評価の `degraded` コントロールは、純粋に物理モデルの生成器だけで
  構成されたプリセット(`impact` の 12 プリセットすべてが、取り除くもの
  が他に何もない単一の `modal` ノードです)については、「フィルタとエン
  ベロープだけ」以上のものを必然的に変えることになります -
  `clap-degrade-graph.mjs` 自身のドキュメントコメントが、degraded セット
  がそうした生成器も単純なノイズに置き換える理由を説明しています。これに
  より、明示的なフィルタ/エンベロープの連鎖を持つプリセットだけでなく、
  すべてのプリセットに対してこのコントロールが意味を持つようになります。
- CLAP の検索精度は、汎用のテキスト・音声モデルの埋め込み空間が、これら
  の音をプロンプトの説明どおりに分離できているかどうかを測るものです。上
  記のリスニングレポートを人間が聴くことの代わりにはならず、両者は一方が
  他方の代わりになるのではなく、並べて報告しています。

<a id="testing-and-ci"></a>
## テストと CI

```bash
pnpm --filter sfx-engine test:unit          # node --test で test/*.test.mjs を実行、166 ケース
pnpm --filter sfx-engine test:hash-fixture  # 53 プリセット x シード 3 個をコミット済み SHA-256 フィクスチャと照合
pnpm --filter sfx-engine test:perf-budget   # 全プリセットをコミット済みの時間ベースラインと照合、3 倍で回帰ゲート
```

`build` と `typecheck` を合わせたこの 3 つが `sfx-engine` の CI ジョブ
(`.github/workflows/ci.yml`)です - 高速で、モノレポの他の部分から完全に
独立しています。すべてのプリミティブは解析的な期待値に対してテストされて
います(オシレーターの周波数はゼロクロス回数で、フィルタのカットオフは測
定した -3dB 点で、といった具合です)。`analysis/signal-checks.ts` のすべ
てのチェックには、肯定側と否定側(そのチェックにわざと違反するように作ら
れ、実際に検知することを証明するもの)の両方のテストがあります。CI から
意図的に除外している、ローカル限定のツールは以下のとおりです: `parity/`
のクロスエンジン Chromium/Firefox/WebKit 決定論性チェック
(`pnpm --filter sfx-engine parity:check`)、ffmpeg とのラウドネス突き合
わせ(`pnpm --filter sfx-engine loudness:ffmpeg-check`)、リスニングレポ
ート、そして CLAP 評価 - いずれも実ブラウザエンジンか外部ツールが必要で、
CI には積んでいません。
